# 对话框不是终点：ToB 的 Agent 交互是"意图入口 + 生成组件 + 可撤销对齐"

> 在采购系统右下角加一个聊天框，为什么没有减少任何一次点击？

## 引子：一个采购审批，五次跳转，聊天框帮不上忙

下面是一个典型场景，菜单数量与公司为示意。

某公司的采购系统有几十个一级菜单、数百个二级页面。一个采购专员要完成"确认 A 供应商资质并发起审批"，实际路径是：供应商列表 → 筛选 → 打开详情 → 找到资质附件 → 下载证书 → 复制证书号 → 打开采购单 → 粘贴证书号 → 选审批人 → 提交。中间还要去法务群问一句"这家有没有诉讼记录"。

产品团队引入了 AI 助手，在右下角加了一个聊天框。用户问："A 供应商的资质有没有问题？"助手答得很流畅，列出了营业执照、ISO 证书、过往合作记录，还提示"未发现明显风险"。

然后用户还是得自己打开供应商详情页、下载附件、复制证书号、填采购单、选审批人。聊天框只是一个更聪明的搜索框，它没有承接任何一次动作，也没有减少任何一次跳转。

问题不在模型。问题在于产品把 Agent 当成了"回答问题的窗口"，而不是"承接意图、生成界面、执行动作、允许撤回"的交互层。ToB 软件的复杂度从来不在功能数量，而在三件事：用户能不能把意图说清楚、界面能不能承载高密度信息、出了事谁来负责。只加一个聊天框，三件事一件都没解决。

这篇文章回答：**Agent 时代 ToB 软件的交互应该怎么设计，才能让 LUI 的意图表达、GUI 的精确控制、以及可撤销的责任机制同时成立。**

## 核心结论

1. **LUI 是意图入口，不是结果展示器。** 对话框负责把模糊需求转成结构化目标；高密度信息、精确参数、批量操作仍然要交给 GUI 组件。二者不是替代关系。

2. **何时用 LUI、何时用 GUI，应由调度层按"意图复杂度 × 信息密度 × 风险等级"决定，而不是由设计师预先写死。** 简单指令给轻反馈，复杂分析生成 Dashboard，手动接管回到全屏控制台。

3. **ToB 交互的信任由三件事构成：过程可见、来源可查、动作可撤销。** 缺一条，用户就只在低风险场景使用；三条都缺，Agent 会退化成"玩具"。

4. **生成式 UI 的工程前提是组件原子化、Schema 优先、白名单沙箱、流式渲染、可访问性。** 没有这五项，"动态生成"会变成"动态幻觉组件"。

5. **RICH 是检查表，不是系统架构。** Intention、Role、Conversation、Hybrid UI 分属逻辑、配置、流程、视图四个层级，并列使用会导致"每个词都对，但拼不成系统"。

6. **IDEA 四层（Intent → Dispatch → Element → Alignment）是按控制流分层，能回答 RICH 没回答的问题：什么时候该生成界面，什么时候不该。** 这是本文提出的框架，不是行业标准，需要用产品数据检验。

7. **可撤销性是 ToB Agent 的硬门槛，不是加分项。** 不可逆动作必须走"预演—确认—双人/双因子"，并且每一步有 pending / executing / done / undone 状态。没有撤销，就没有授权。

8. **"未来都是对话框"和"未来都是生成式 UI"都是错的。** 更可能的终局是"静态底座 + 生成组件 + 可撤销对齐"：页面还在，但交互粒度从页面级降到组件级。

## 一、问题为何成立：ToB 的复杂度不在功能，在意图与责任

### 1.1 旧范式：人适应系统

过去二十年，ToB 软件形成了稳定范式：左侧菜单树、中间数据表格、顶部筛选器。它通过把业务流程抽象成标准功能模块，解决了信息化问题。代价是用户要接受培训、记忆路径、用点击驱动软件。功能越多，菜单越深，认知负荷越重。

这套范式的隐含假设是：用户的需求可枚举，操作路径线性。但真实需求是发散的。"分析上季度华东销售异常并给整改建议"涉及查数、对比、归因、生成建议，没有一个预设页面能覆盖。用户只能在多个页面之间跳转，思维流被打断。

### 1.2 加聊天框的三种失败

**外挂查询。** 聊天框能回答，但不能承接动作。用户拿到答案后还要自己复制、粘贴、跳转。AI 成了"更聪明的搜索"，没有进入工作流。

**意图丢失。** 用户说"把这个单子加急"，助手回答"好的，已记录"。但"加急"在系统里意味着改优先级、通知仓配、跳过某个审批节点。自然语言到结构化动作之间，缺一层显式的意图解析与确认。

**责任真空。** 助手建议"这家供应商可以合作"，用户照做，出了合规问题。谁签字？聊天记录能不能作为审批凭证？如果 Agent 自动发了邮件、改了数据，责任落在谁头上？没有答案，用户就只在低风险场景使用。

### 1.3 三个变量

把交互设计问题拆成三个可观察的量。

**意图带宽。** 用户表达一个目标需要多少次操作、多少认知负荷。菜单导航的带宽低（要点五次），自然语言高（一句话），但自然语言有歧义，需要澄清。

**信息密度。** 一个决策需要看多少结构化信息。审批需要看金额、供应商、历史履约、风险标签、附件；纯文本承载不了，表格和卡片可以。

**责任可转移性。** 这个动作出错后，能否回滚、能否追责、能否由人签字。可逆、低金额、内部操作，责任容易转移；不可逆、对外、高金额，责任必须留在人。

三个变量决定界面形态，不是设计师的偏好。

## 二、三种路径对比

**路径 A：纯 LUI。** 所有操作都通过对话完成，界面只剩一个输入框和消息流。优点是意图表达最自然、学习成本最低；缺点是信息密度低、精确控制弱、可发现性差，复杂审批和多维分析很难在气泡里完成。

**路径 B：纯 GUI。** 保持现有页面与表单，AI 只在后台做推荐。优点是可控、可审计、用户熟悉；缺点是意图表达仍然要学菜单，AI 的价值被限制在"提示"。

**路径 C：混合。** LUI 做意图入口与解释，GUI 做高密度展示与精确控制，生成式组件按需插入对话流，静态页面作为底座保留。优点是兼顾表达与可控；缺点是工程复杂，需要组件原子化、Schema、白名单、评测。

推荐 C，但不是所有场景都用 C。高频、精密、强合规的操作（财务过账、生产排程）继续用 B；低频、发散、探索性的任务（分析、诊断、方案草稿）用 C；纯查询用 A 的轻量形态即可。

## 三、设计原则

### 原则 1：LUI 负责"要什么"，GUI 负责"是什么、改什么"

对话框不应该承担复杂表格和精确参数。它负责把"帮我看看这个供应商"转成结构化意图，然后由调度层决定：生成一张供应商卡片、打开详情页、还是直接给出结论。

判断标准：如果用户需要在多个字段之间对比、批量选择、精确输入数值，就用 GUI；如果用户表达的是目标、原因、约束，就用 LUI。

### 原则 2：按意图复杂度切换形态，不搞一刀切

简单指令不生成新界面，只在状态栏给轻反馈；复杂指令才生成 Dashboard；手动接管时把聊天框收起，回到全屏控制台。这条规则比"未来都是对话框"或"未来都是生成式 UI"都更可操作。

### 原则 3：渐进披露

ToB 业务逻辑复杂，一次性生成庞大表单会造成视觉压力。骨架屏先给出结构，数据到位再填充；次要信息默认折叠，用户需要时展开；多步任务分步确认，不把所有字段堆在一屏。

### 原则 4：过程可见、来源可查

过程可见不是把模型的完整思维链原样输出，而是给出可理解的步骤："正在查供应商主数据""正在比对诉讼记录""已找到 2 条风险提示"。来源可查是每个关键数字能点回原文：合同第几条、报表哪一页、数据哪一天。

没有来源的自信回答，比明确的"我不知道"更危险。ToB 场景里，准确性优先于创造性。

### 原则 5：动作可撤销

这是 ToB 与 ToC 最大的区别。ToC 的聊天机器人答错了，用户笑一笑；ToB 的 Agent 改错了一个字段、发错了一封邮件、批错了一笔款，可能是事故。

所有动作要有状态：pending（待确认）、executing（执行中）、done（完成）、failed（失败）、undone（已撤销）。破坏性动作要有预演：先展示"将要改什么、影响哪些记录、能否回滚"，再让用户确认。不可逆动作要双人/双因子。

### 原则 6：组件白名单与 Schema 优先

生成式 UI 不能允许模型随意输出 HTML。正确做法是：前端维护一套原子组件库，模型只输出"组件类型 + 属性"的 JSON，前端做白名单映射；Schema 定义组件的可用属性、数据类型、取值范围；未知组件直接拒绝，降级为文本。

白名单越严，越安全但越像旧表单；越松，越灵活但越容易出现幻觉组件。平衡点是：覆盖 80% 常见表达，剩余 20% 用文本 + 链接兜底。

### 原则 7：责任分层

按风险分三区：绿区（内部测试数据、低额退款、样式修复）Agent 自主执行；黄区（对外邮件、非核心发布）先执行后 24 小时内抽样审计；红区（转账、核心库、权限变更、对外合同）Agent 只出方案和仿真，人输入密钥执行并签字。

签字的人享有最终裁决权，也承担直接责任。Agent 没有法律主体资格，不能成为责任终点。

## 四、接口与结构

### 4.1 IDEA 四层

**Intent（意图层）。** 把语音、文本、点击统一解析成结构化目标。比如"把华南区的分货权重改成 1.2"解析为 `{action:"update_allocation", region:"south", weight:1.2}`。多模态输入必须归一到同一个 Intent 对象，否则后续无法复用。

**Dispatch（调度层）。** 决定这个意图要做什么：查数据、调工具、生成界面、还是直接回答。它也是"何时 GUI 何时 LUI"的决策点。放在前端延迟低但权限弱，放在后端可控但每次交互要往返；常见做法是轻量路由在前端/边缘，重决策在后端。

**Element（元素层）。** UI = f(Intent, Data)。按意图和数据生成组件，而不是预写页面。生成的是组件树，不是整页 HTML。

**Alignment（对齐层）。** 中间态展示、确认、打断、回滚。用户的反馈作为新 Context 进入下一次 Intent 解析，形成闭环。

四层与 RICH 的差别在于：RICH 是四个并列的要素，IDEA 是四层递进的控制流。RICH 告诉你"要有混合界面"，IDEA 告诉你"由调度层决定什么时候混合"。

### 4.2 一条消息的结构

```json
{
  "role": "assistant",
  "blocks": [
    {"type": "reasoning", "collapsed": true,
     "steps": ["查询供应商主数据", "比对诉讼记录", "汇总资质有效期"]},
    {"type": "answer", "format": "markdown", "content": "..."},
    {"type": "sources", "items": [
      {"title": "营业执照", "doc_id": "SUP-8842", "page": 1, "updated_at": "2026-03-11"},
      {"title": "诉讼记录查询", "source": "法务系统", "queried_at": "2026-10-24T09:12:31+08:00"}
    ]},
    {"type": "actions", "items": [
      {"label": "发起审批", "verb": "create_approval", "risk": "yellow",
       "requires_confirm": true},
      {"label": "标记风险", "verb": "flag_risk", "risk": "green"}
    ]}
  ],
  "status": "completed"
}
```

字段名是本文约定的示例，不是某个产品的官方协议。要点是：思考、回答、来源、行动四段分离；每一段有自己的状态；行动带风险等级和确认要求。

### 4.3 生成式组件的 Schema

```json
{
  "component": "data_table",
  "props": {
    "columns": [
      {"key": "supplier", "label": "供应商", "type": "string"},
      {"key": "amount", "label": "金额", "type": "number", "unit": "CNY"},
      {"key": "risk", "label": "风险", "type": "enum", "values": ["低", "中", "高"]}
    ],
    "rows": [["A 公司", 128000, "中"], ["B 公司", 96000, "低"]],
    "actions": [{"label": "查看详情", "verb": "open_detail"}]
  },
  "fallback": "text"
}
```

前端只认识白名单里的 `component`；`props` 要过 Schema 校验；校验失败或组件未知，降级为 `fallback` 文本。这样模型有表达自由，但没有任意执行权。

### 4.4 可撤销的状态机

```
draft ──confirm──→ pending ──approve──→ executing ──success──→ done
  │                   │                    │
  │                   └──cancel──→ cancelled└──fail──→ failed
  │
  └──discard──→ discarded

done ──undo(window=24h)──→ undone
```

`undo` 要有时间窗和权限校验；超过窗口只能走反向流程（冲正、撤回审批），不能直接改历史。审计日志记录每一步的操作者、时间、前后值。

### 4.5 形态选择的伪代码

```
function chooseSurface(intent, data, risk):
    if risk == "irreversible":
        return FullScreenReview + DualApproval
    if intent.complexity == "low" and data.density == "low":
        return InlineFeedback
    if intent.complexity == "medium" and data.density == "high":
        return GeneratedCard(intent, data)
    if intent.requires_precise_control:
        return FullScreenConsole
    return ChatAnswer + SuggestedActions
```

这是伪代码，不是可直接运行的实现。它的价值在于把"界面形态"从设计偏好变成可讨论的规则：输入是意图、数据、风险，输出是形态。

## 五、反模式

| 反模式 | 诊断 | 修法 |
|---|---|---|
| 右下角聊天框 | AI 是外挂，不承接动作 | 让回答直接带可执行 action，或嵌入当前页面 |
| 用生成整页替代组件 | 每次生成整页，状态不可控、性能差 | 生成组件树，页面壳保持稳定 |
| 无来源的自信回答 | 用户无法验证，出事无法追溯 | 关键数字强制引用，无来源标注"未核实" |
| 只有"停止生成"，没有"撤销动作" | 生成可停，执行不可逆 | 动作级 undo + 审批 + 审计 |
| 组件白名单过松 | 模型输出未知组件/恶意 props | Schema 校验 + 白名单 + 文本兜底 |
| 组件白名单过紧 | 生成 UI 退化成旧表单 | 覆盖 80% 常见表达，保留组合能力 |
| 把聊天记录当审批凭证 | 对话不可审计、可被编辑 | 结构化审批单 + 签字 + 日志 |
| 动态 UI 不做可访问性 | 键盘、读屏、RTL 全部失效 | 组件库内置 a11y，生成时校验 |
| 把 RICH 当架构 | 四个概念不在同一层级，无法指导实现 | 用 IDEA 的控制流分层替代 |
| 用 LUI 做精确参数输入 | 自然语言有歧义，改一个数值要来回确认 | 数值/批量/对比用 GUI |

反模式 1 是最常见的。判断一个 ToB AI 功能是不是外挂，有一个简单测试：**用户拿到回答后，还需要复制粘贴几次？** 如果超过一次，说明它没有进入工作流。

## 六、验证方式

### 6.1 任务完成率与首次成功率

传统 GUI 用点击路径和错误率衡量；Agent 界面要用"任务完成率"（用户是否达成目标）和"首次成功率"（不返工一次完成）。两者要分开：完成率低是能力问题，首次成功率低是交互问题。

### 6.2 可复现性

同一个意图、同一份数据，生成的组件集合是否稳定？如果每次生成的结构差异很大，用户无法形成肌肉记忆，A/B 测试也无法做。可复现性不是要求像素一致，而是要求"关键信息不丢、关键动作位置稳定"。

### 6.3 可访问性

动态生成的面板必须保证键盘导航、读屏标签、对比度、RTL 布局。生成式 UI 的可访问性不能靠"生成后再补"，要在组件库和 Schema 层内置约束。

### 6.4 纠错成本

用户发现 Agent 做错后，纠正需要几步、多少时间？指标是"撤销耗时"和"纠错步数"。如果一个错误要用户跳五个页面才能改回来，可撤销性就是假的。

### 6.5 信任指标

来源点击率、步骤展开率、人工接管率、红区签字覆盖率。来源点击率低不一定是好事，可能说明用户根本没在验证；人工接管率高说明 Agent 的能力边界没划清。

### 6.6 一个可执行的测试协议

选 20 个真实任务、5 名真实用户，分两组：一组用旧界面，一组用混合界面。记录四个数：任务完成率、首次成功率、完成时间、求助次数。再加两个专项测试。

**可复现性测试**：同一个意图、同一份数据，连续生成 10 次，比较关键信息是否出现、关键动作是否在稳定位置。不要求像素一致，要求"用户第二次能凭记忆找到"。

**撤销测试**：让用户执行一个黄区动作，然后在 30 秒内撤销，记录撤销步数与耗时；再测一次超过 undo 窗口的撤销，确认系统引导到反向流程而不是直接改历史。撤销耗时超过人工重做时间，说明可撤销性是假的。

测试要在真实数据上做，不能用精心准备的 demo 数据。demo 数据没有脏值、没有权限冲突、没有超长附件，恰好绕开了最容易出问题的地方。

## 七、从 WIMP 到生成式：交互变迁的底层逻辑

### 7.1 WIMP 的确定性优势

WIMP 指窗口、图标、菜单、指针。它统治三十年，核心优势是确定性：点什么就是什么，符合物理直觉，适合高频、精密操作。无人机摇杆、财务过账、CAD 绘图，今天仍然需要 WIMP 式的直接控制。

WIMP 的墙在意图表达。当需求变成"分析数据并把异常发给王总"，点击路径会拉得很长；静态界面无法穷举所有场景，功能越堆越多，出现大量"僵尸功能"。

### 7.2 移动交互的启示

移动互联网没有推翻 WIMP，而是用隐喻压缩路径：手势直接作用于内容（滑动删除、捏合缩放），下拉刷新利用"拉"的物理隐喻，Toast 用非模态反馈替代打断式弹窗，底部导航尊重拇指热区，无限滚动用"流"替代分页。

这些设计的共同点是：**降低每一步的摩擦，而不是增加功能**。Agent 交互应该继承这个思路：不是加一个聊天框，而是让意图到动作的路径变短。

### 7.3 静态渲染到生成式 UI

传统模式是 UI = f(State)，状态变了界面变，但 f 是写死的。Agent 模式是 UI = f(Intent, Data, Components)，意图决定展示什么组件，数据决定填充什么，组件库提供原子能力。

这不是消灭菜单和页面。页面仍然存在，作为稳定底座；生成的是页面内的组件、卡片、表格、审批流。交互粒度从"页面级"降到"组件级"。

### 7.4 对工程架构的影响

组件要原子化、去业务耦合，才能被 Agent 拼装；前后端协议从"传数据"变成"传数据 + 界面描述"；需要 Schema/DSL 描述界面结构；需要白名单沙箱防止幻觉组件；需要流式渲染和骨架屏处理延迟；需要可访问性约束。

这也是为什么"生成式 UI"不是一个前端特效，而是一次架构调整。

### 7.5 三个没有变的东西

技术从 WIMP 到移动再到 Agent，有三件事始终没变，它们决定了新范式不能推翻旧范式。

**信息密度需要载体。** 一张 50 行的审批表、一张多维对比图、一段带时间轴的日志，用自然语言复述只会更长、更难扫。GUI 的表格、图表、卡片不是历史包袱，是人类视觉系统的高带宽通道。LUI 负责把用户带到正确的表，GUI 负责让用户在表里做决定。

**责任需要归属。** 谁发起、谁审批、谁执行、谁签字，必须有结构化记录。聊天记录可以被编辑、可以被解释、可以没有上下文；审批单有字段、有版本、有签名。ToB 的合规不是不信任 AI，而是不信任"没有凭证的口头承诺"。

**高频操作需要肌肉记忆。** 财务每天过账、客服每天建单、运维每天发布，这些动作重复上千次，用户需要的是快捷键、批量选择、固定位置，而不是每次重新描述一遍意图。Agent 应该优化低频发散任务，不应该强迫高频用户改用对话。

这三条决定了混合界面的基本分工：LUI 处理"第一次"和"例外"，GUI 处理"第 N 次"和"标准"。

## 八、信任与可撤销性：ToB 的硬门槛

ToB 用户不要求 Agent 永不犯错，要求犯错后能发现、能纠正、能追责。三件事对应三种设计。

**能发现**：过程可见、来源可查、异常提示。Agent 不确定时要说"不确定"，而不是编一个答案。

**能纠正**：动作级 undo、参数可编辑、对话可打断、任务可暂停。撤销不是"重新生成一版"，而是把系统状态恢复到执行前。

**能追责**：审计日志记录谁在什么时候让 Agent 做了什么、依据是什么、谁签的字。红区动作必须有人签字，签字人要承担直接责任。

可撤销性还有一个组织含义：它决定了授权的边界。如果一件事不可撤销，人就不敢把决定权交给 Agent；如果可撤销，人可以给更大的 autonomy。所以投资撤销机制，本质上是在扩大 Agent 的能力半径。

### 8.1 一个红区动作的完整链路

以"给 A 供应商支付 128,000 元"为例，看可撤销性怎么落到每一步。

**解析。** 用户说"把 A 公司这笔款付了"。Intent 解析出收款方、金额、合同号、付款条件；缺哪个字段就追问，不猜。

**定级。** 金额超过阈值、对外支付、不可逆，判为红区。

**预演。** 系统展示：当前账户余额、合同应付金额、历史付款记录、是否重复付款、审批链、预计到账时间。预演结果是一张 diff 卡，不是一段话。

**确认。** 需要业务负责人和财务双人确认；确认动作带时间戳和身份；Agent 不能代替任何一方点击。

**执行。** 用幂等键提交，防止网络超时重试导致重复付款；执行中状态可见；失败返回结构化原因（余额不足、账户冻结、超出限额），不是"支付失败"四个字。

**留痕。** 记录谁发起、谁审批、依据哪份合同、Agent 生成了什么建议、人改了什么。

**撤销。** 支付完成后不能删除记录，只能走冲正或退款流程；undo 窗口内可以撤回未提交的指令，窗口外只能走反向流程。这条限制不是技术保守，是财务合规的要求。

整条链路里，Agent 做了大量工作：解析、查数、比对、生成 diff、预填单子。但它没有签字权，也没有绕过幂等和审计。这才是"可撤销"的真实含义：不是假装错误没发生，而是让每一步都能被回退或被追责。

### 8.2 信任的建立顺序

信任不是一次性给的，是按风险逐步开放的。先让 Agent 做只读查询，用户验证来源；再让它做可撤销的绿区动作，用户验证撤销；再做黄区动作，用户验证抽样审计；最后才讨论红区方案生成。跳过任何一步，都会在事故后回退到起点。

这也解释了为什么很多 ToB AI 功能停在"查询"：不是模型不行，是撤销、审计、签字的基础设施没建好。

## 九、情景推演

**基准情景（概率 55%）：混合界面成为 ToB 主流。**
触发条件：组件库与 Schema 逐步标准化；企业接受"AI 出草稿、人签字"；评测从点击率转向任务完成率。
2029 年图景：静态底座 + 生成组件成为常见形态；LUI 承担意图与解释，GUI 承担审批与精确控制；生成式 UI 在分析、诊断、客服场景普及，在财务过账、生产排程等强合规场景仍以传统界面为主。
验证指标：混合界面产品的任务完成率；生成组件的白名单命中率；人工接管率。

**乐观情景（概率 20%）：协议与组件标准统一，生成式 UI 可评测。**
触发条件：出现跨厂商的组件 Schema 标准；可访问性与安全约束内置；A/B 测试方法成熟。
2029 年图景：Agent 能稳定生成可复现的组件树；动态 UI 的评测像今天的 Web 性能一样有标准；ToB 软件的"页面"概念弱化，变成"能力 + 组件 + 编排"。
验证指标：跨产品组件复用率；可复现性评分；可访问性通过率。

**悲观情景（概率 25%）：生成式 UI 不可维护，回退到"聊天框 + 固定卡片"。**
触发条件：生成组件不可复现、不可访问、频繁幻觉；一次合规事故导致企业收紧；维护成本高于收益。
2029 年图景：企业只保留"对话 + 预置卡片"，动态生成被限制在低风险场景；前端工作量回流到固定组件；Agent 交互退化为高级搜索。
验证指标：生成组件的事故率；维护成本占比；动态 UI 功能下线率。

## 十、行动方案

**0–1 个月：定边界。**
盘点现有 ToB 流程，按"意图复杂度 × 信息密度 × 风险"分类；选出 3 个高频、低风险、信息密度中等的场景做试点（如供应商查询、报表解释、工单草稿）；为每个场景定义 LUI 入口、GUI 承载、撤销方式。

**1–3 个月：建组件与 Schema。**
把页面拆成原子组件（表格、卡片、图表、表单、审批流）；为每个组件定义 Schema（属性、类型、取值范围、a11y 约束）；建白名单渲染器与文本兜底；接流式渲染与骨架屏。

**3–6 个月：接动作与撤销。**
把"回答"升级为"回答 + 行动"；每个行动带风险等级、确认要求、undo 窗口；红区接双人确认与审计日志；建立任务完成率、首次成功率、撤销耗时三个指标。

**优先级。**
先做"可撤销的低风险动作"，再做"不可逆动作的方案生成"，最后才做"红区自主执行"。顺序反了，一次事故就会让项目停摆。

**退出条件。**
任务完成率连续两个月低于基线；撤销耗时超过人工重做时间；出现一次无审计的红区动作；可访问性检查不通过。触发任一条，暂停动态 UI 扩张，回到固定组件。

## 十一、风险与反方观点

**反方一：对话框只是过渡形态，终局是"无界面"。** 可能。如果 Agent 能可靠地替用户完成大部分任务，界面会退到后台。但在 ToB 场景，审批、审计、责任签字需要可见的载体，"无界面"很难满足合规。更现实的终局是"界面变薄，但不消失"。

**反方二：生成式 UI 的评测做不了。** 传统 GUI 可以用任务完成率、点击路径、错误率；动态界面每次不同，A/B 测试难。这个批评成立，也是当前最大空白。缓解办法是评"关键信息是否出现、关键动作是否可用、结构是否稳定"，而不是评像素。

**反方三：LUI 效率低。** 对高频精确操作，说话比点击慢，而且有歧义。同意。所以 LUI 不应该替代快捷键和表单，只应该承接"意图表达"和"解释"。

**反方四：可撤销性会被滥用。** 用户可能随意执行再撤销，产生大量无效操作和审计噪音。需要 undo 窗口、频率限制、撤销原因记录；红区动作不允许"先做再撤"。

**反方五：RICH 的批评是过度解读。** "为了凑缩写"是评价，不是事实。Ant Design X 是否这样定位，无法从公开材料确认。可以成立的批评是"四者抽象层级不一致"，而不是动机揣测。本文保留这个限定。

**反方六：IDEA 只是又一个框架。** 成立。IDEA 是本文提出的控制流分层，没有经过大规模产品验证。它的价值是提供一个可讨论的结构，不是宣称唯一正确。如果产品数据证明"调度层放在后端导致延迟不可接受"，框架就要改。

**反方七：生成式 UI 会加剧厂商锁定。** 如果 Schema、组件库、渲染器都是私有标准，迁移成本会很高。缓解办法是尽量复用 Web Components、OpenTelemetry 这类通用层，把私有部分限制在编排与策略。

## 十二、跟踪指标与触发规则

| 指标 | 口径 | 目标/阈值 | 触发动作 |
|---|---|---|---|
| 任务完成率 | 用户达成目标的比例 | ≥基线 +10% | 低于基线查意图解析 |
| 首次成功率 | 不返工一次完成 | ≥70% | 低于阈值查澄清与确认 |
| 平均交互轮次 | 每任务对话轮数 | 稳定或下降 | 上升查意图歧义 |
| 人工接管率 | 需人工接手的任务占比 | <30% | >50% 查能力边界 |
| 撤销成功率 | undo 成功比例 | ≥99% | 低于阈值修状态机 |
| 撤销耗时 | 从发现错误到恢复 | <2 分钟 | 超标简化路径 |
| 来源点击率 | 关键回答被验证比例 | 10%–30% | 过低说明未验证 |
| 无来源回答占比 | 关键数字无引用 | <5% | 超标强制引用 |
| 可访问性通过率 | 键盘/读屏/RTL 检查 | 100% | 不通过禁止上线 |
| 生成组件命中率 | 白名单组件成功渲染 | ≥95% | 低于阈值扩组件库 |

规则示例：撤销成功率低于 99%，暂停所有黄区动作；无来源回答占比超过 5%，强制走"带引用"模板；可访问性检查不通过，动态 UI 不允许进入生产。

## 事实核查与批判性审查

> 本节逐条核查报告所依赖的关键说法。判定标准：只抓硬事实（日期、人物、定义、公式、单位、换算、算术、来源、A 当 B）；预测未兑现、数据截至某时点、观点分歧不算错误。

### 核查范围与方法

- **框架归属**：RICH 是 Ant Design X 的设计理念还是行业架构；IDEA 是不是本文自创。
- **产品形态**：WPS 灵犀、秘塔研究版等交互形态是否被写成稳定事实。
- **工程标准**：组件白名单、JSON Schema 渲染是否已成为统一行业协议。
- **因果表述**：把“GUI 会变成对话框”“SCQA 可组织全文”这类预测或方法误用，改成有范围的判断。
- **设计目标值**：首次成功率 70%、撤销耗时 2 分钟、白名单覆盖 80% 等，是目标还是实测。

交叉核对方式：Ant Design X 公开文档、产品公开页面、设计与写作方法论原典；无法确认动机与内部定位的，标“评价”或“待核实”。证据等级：A=原始披露或权威指南；B=多源一致；C=单一来源；D=推算或待核实。

本分类的审查表里没有针对本报主题的硬事实错误条目。本报以设计推演为主，核查重点不是数字对错，而是“把评价当事实、把自创框架当共识、把工程方向当标准”这三类表述。核查后未发现日期、单位、算术类的硬错误。

| WPS 灵犀“左文档右 AI”、秘塔研究版“多智能体流程图” | 版本时点当永久事实 | 只能标注为“截至 2026 年中的观察”，产品形态随版本变化 | C：公开产品页面 |
| “GUI 会变成对话窗口” | 预测当结论 | 对话框是意图入口，结果仍由 GUI 组件承载；更准确的判断是“界面变薄，但不消失” | B：交互机制推理 |
| “SCQA 可以用来组织全文” | 方法误用 | SCQA 只负责开头，主体要用金字塔原理展开；这是方法限定，不是事实错误 | B：明托方法论原典 |

### 待核实与证据边界

- **RICH 的官方定位**：公开材料能确认四个词，不能确认“是否为了凑缩写”。任何动机判断都是评价，不是事实。
- **IDEA 的产品效果**：没有 A/B 数据、没有跨产品复现；“调度层放前端还是后端”的延迟与权限权衡，仍是待验证的工程选择。
- **“组件白名单覆盖 80% 常见表达”**：经验值，缺场景分布与统计口径；白名单过紧会退化成旧表单，过松会出幻觉组件，平衡点需要按产品数据调。
- **“撤销耗时 <2 分钟”“首次成功率 ≥70%”**：目标值，不是行业基准；不同业务的可接受阈值不同。
- **竞品形态**：Microsoft Copilot、Notion AI、GitHub Copilot、Salesforce Einstein 的具体交互随版本变化；文中只用于示意，不作竞争结论。
- **情景概率（55%/20%/25%）**：作者判断，不是统计。
- **“ToB 与 ToC 最大的区别是可撤销性”**：是重要差异，不是唯一差异；合规、审计、责任结构同样关键，这句话应理解为优先级判断。

### 对报告结论的影响

- **删掉“RICH 凑缩写”的动机判断后，结论 5 反而更稳**：RICH 作为检查表仍然有用，问题只在“四者不在同一层级、不能当架构”；这正好支撑 IDEA 的必要性，而不是否定 RICH 的全部内容。
- **IDEA 被明确为待验证框架后，结论 6 的置信度下调**：它不再是“能回答 RICH 没回答的问题”的既成方案，而是一个可讨论的控制流假设；读者应把它当作产品实验的起点，不是标准答案。
- **Schema/白名单降级为工程方向后，结论 4 的落地成本上升**：五项前提（组件原子化、Schema 优先、白名单沙箱、流式渲染、可访问性）仍然成立，但不能假设“照着一个标准接就行”；每家企业都要自建组件库与校验层。
- **产品形态加时间限定后，竞品论证不受影响**：本文的核心论证是“聊天框不承接动作”，不依赖 WPS 或秘塔的具体布局；即使这些产品后来改版，机制判断仍成立。
- **“GUI 变对话窗口”修正与结论 8 一致**：终局是“静态底座 + 生成组件 + 可撤销对齐”，不是纯对话；这条修正消除了原文里的一处绝对化表述。
- **SCQA 修正只影响写作方法**：不改变任何产品结论；它提醒读者，框架的适用范围要写清楚，不能把开头工具当全文结构。
- **需要打折的结论**：三情景概率、目标指标、白名单覆盖率都是判断或目标；相对稳健的是机制层结论——LUI 负责意图、GUI 负责高信息密度与精确控制、不可逆动作必须预演/确认/可撤销、没有来源的自信回答比“我不知道”更危险。
