# 给 Agent 造一套能自证的工程外壳：工具、状态、循环与门禁的设计

> 同一台设备、同一个模型，为什么演示能跑通，生产却把"成功"执行成了事故？

## 引子：六步都返回 ok，任务却失败了

一台巡检设备接到指令："去 A-03 区域看看有没有违停车辆，有就取证并劝离。"

Agent 按它看到的接口编排：暂停当前路线、移动到目标附近、调整观测模块、拍照、播报、恢复路线。六个调用依次返回 `ok`。Agent 在日志里写下"任务完成"。

真实发生的是：`pause` 在路线还没真正停稳时就返回了成功；`move_to` 第一次超时，Agent 重试，设备已经偏离原路线；`aim` 锁定的是一个即将离开画面的目标；`capture` 拍到的是一张空帧；`speaker_play` 对着空气播报；`resume` 因为断点失效而失败。六步单看都成功，整体却没有一步真正达成意图。

这不是模型不够聪明。把同样的六个动作交给一个人类工程师，他会知道"暂停要等状态稳定""移动超时不能直接重试""锁定后要确认目标还在""恢复路线前要检查断点"。这些知识没有写在任何一个 API 的 schema 里，人类靠经验补，Agent 只能靠猜。

这篇文章回答一个问题：**一个复杂系统要向 Agent 开放能力，接口、状态、循环、门禁应该怎么设计，才能让"每一步成功"等于"整体成功"。**

## 核心结论

1. **Agent = Model + Harness。** 模型能力在收敛，harness 工程在分化。同一底座模型，工具契约、上下文管理、权限门禁、循环终止条件不同，任务成功率可以差出数倍。

2. **工具应该封装"原子意图"，不是"原子动作"。** 把 50 个原子 API 暴露给模型，端到端成功率按 pⁿ 衰减；合成 5 个有状态的高层工具，等于把 n 压小。这是提升可靠性最直接、最不依赖模型升级的杠杆。

3. **工具接口按五个正交平面设计：控制、事件、状态、事实、安全。** "状态面 vs 事实面"的分离最关键：状态是易逝快照（电量、坐标、链路），事实是持久业务结果（目标 ID、抓拍路径、巡检结论）。混在一起，模型会把"查了状态"误当成"改了状态"。

4. **Tools、Skills、MCP 是三个层次，不是三个竞品。** Tools 是原子执行单元；Skills 是"工具 + 知识 + 推理"的任务级封装，可近似写成 Skills = (Tools + Knowledge) × Reasoning；MCP 是客户端—服务器—模型之间的连接协议。

5. **状态管理是当前最大的工程债。** 无状态推理 API 迫使应用层手动拼 prompt 来模拟状态。需要修正一个常见说法：无状态 API 并不是"每次调用都丢弃全部 KV Cache"——主流厂商已有 prompt caching，前缀 KV 可跨调用复用；真正没有原生承载的是应用自定义状态。

6. **循环要分两层：会话层管多轮状态，执行层管单轮执行。** 两层用异步生成器连接。循环必须有预算、最大步数、幂等键、检查点和显式终止条件，否则"自愈"会变成"死循环烧钱"。

7. **人要在三个地方介入：元规则变更、边界外异常、非确定性语义审查。** 流程不完善时，一连串绿色门禁必然降低警觉，这是自动化偏见的稳定结论，不是偶发心态。

8. **Harness 自循环只在"断言可穷举、mock 可覆盖"的子域可靠。** 它会语义漂移、过拟合 harness、被 mock 欺骗、被奖励黑客利用。把它当成能自我证明的系统，是这一类架构最大的风险。

## 一、问题为何成立：原子 API 把复杂性转嫁给了 Agent

### 1.1 步骤数按乘法吞噬成功率

每一步都有出错可能：路线上传失败、观测模块被占用、目标在接近途中丢失、存储空间不足、链路抖动。端到端成功率近似为：

**Success ≈ P(step₁) × P(step₂) × … × P(stepₙ) = pⁿ**

p=0.99、n=50 时约 60.5%；p=0.95、n=30 时约 21.5%。这不是 prompt 能修的问题，问题在 n 本身。把 50 个原子动作合成 5 个有状态意图，等于直接把 n 压到十分之一。

### 1.2 原始数据侵占上下文

"判断画面里有没有静止的违停车"这件事，原子接口返回的是 152 帧、每帧若干检测框、置信度、track_id、速度、坐标。Agent 必须自己在上下文里做过滤、跨帧去重、静止判断、质量过滤。这些计算把真正用于决策的窗口挤掉了。

正确的工具返回的是语义信号：

```json
target_recognition.list_unprocessed(only_when="stationary_confirmed") →
{
  "count": 2,
  "targets": [
    {"id": "T-101", "type": "vehicle", "stationary_duration_s": 73,
     "position_quality": "rough", "can_drive_movement": true},
    {"id": "T-102", "type": "vehicle", "stationary_duration_s": 91,
     "position_quality": "rough", "can_drive_movement": true}
  ]
}
```

Agent 拿到就能直接写 if-else。判断标准只有一句：**它拿到返回值之后，是能直接决策，还是还要先做一遍过滤、聚合、去重？** 如果是后者，信息压缩没有完成。

### 1.3 隐式约束不可见

原子 API 之间有时序、互斥、幂等要求：

- 路线没真正暂停，不能接管移动；
- 观测模块没锁定，拍照可能没有目标；
- 同一目标处理要幂等，网络超时重试不能重复取证、重复播报；
- 电量不足时不应接受远距离移动指令。

人类读了设计文档就懂，Agent 只能从 schema 里看到参数类型。schema 不会写"先暂停再移动"，也不会写"超时不要直接重试"。

### 1.4 根因是复杂性转嫁，不是模型笨

三个问题指向同一件事：**原子 API 把系统内部的复杂性转嫁给了调用方。** 以前调用方是人，人有常识、会查日志、能容忍模糊；现在调用方是 Agent，你给它什么它就信什么，漏一个状态它就缺一个分支。

所以"换更强的模型"只能提高单步 p，不能降低 n，也不能把隐式约束变显式。接口层的债，要在接口层还。

## 二、三种路径对比

**路径 A：全原子 API + 更强 prompt。** 不改接口，靠 few-shot、扩大上下文、优化提示词让 Agent 自己编排。优点是零适配成本；缺点是 1.1–1.3 的三个问题一个都没解决。只适合幂等、无状态依赖、容错高的场景，比如查数据库、发消息、调 SaaS。

**路径 B：预定义工作流 + Agent 只填参数。** 人把流程写死，Agent 只在判断点介入。可靠性最高，不符合安全期望的动作根本编排不出来；缺点是"一个场景跑一万次"可以，"一万个场景各跑一次"成本极高。适合产线、固定巡检路线、强监管流程。

**路径 C：高阶有状态 Tool + Agent 自由编排。** 系统暴露的是封装了状态机、信息压缩、安全门、资源互斥的高层工具，Agent 在能力边界内自由组合。自由度与安全性折中，适配面最广；代价是工具设计投入最大。

**表 5：三条路径的选择**

| 维度 | A 全原子 API | B 预定义工作流 | C 高阶有状态 Tool |
|---|---|---|---|
| 自由度 | 最高 | 最低 | 中高 |
| 可靠性 | 最低 | 最高 | 高 |
| 新场景成本 | 低 | 极高 | 中 |
| 上下文占用 | 高 | 低 | 低 |
| 适用 | 幂等无状态调用 | 固定高风险流程 | 多变但需安全兜底 |

推荐组合：**主流程用 B 保底，分支和新场景用 C 编排，A 只作为逃生舱。** 不是所有场景都需要 Agent 自由编排；选择架构的前提是理解自己场景里确定性与多变性的比例。

## 三、设计原则

### 总原则：职责分界

先回答"这件事该归谁"，而不是"谁方便"。

| 复杂度类型 | 归谁 | 为什么 |
|---|---|---|
| 资源互斥、操作时序 | Tool 内部 | 确定性逻辑，交给不可靠的调用方就是灾难 |
| 原始数据 → 语义信号 | Tool 内部 | 不要把 Agent 的上下文浪费在原始数据上 |
| 安全底线（区域、电量、互斥、幂等） | 系统边界 / Tool 契约 | 不能依赖任何人"记得检查" |
| 业务判断（是否可疑、优先级、是否人工介入） | Agent / 上层编排 / 人 | 随场景变化，Tool 不该理解 |
| 流程编排（先取证还是先播报） | Agent / 工作流 / 策略引擎 | 跨 Tool 的逻辑，Tool 不该知道 |
| 环境状态（负载、并发、降级开关） | 系统只读视图 | 服务编排决策，但不触发动作 |

一句话：**确定性逻辑下沉到 Tool，不确定性判断留给 Agent 或上层，安全底线由系统边界强制执行。**

### 原则 1：状态优先于动作

只列方法不定义状态，Agent 就只能猜。`pause()` 在"已完成"的路线上是拒绝、是重新进入运行、还是静默忽略？三种都可能，Agent 无法判断。

每个动作都必须绑定状态迁移，并告诉 Agent"接下来能做什么"：

```json
// pause() 在 completed 状态下返回
{"status": "already_completed", "reason": "route_finished",
 "suggestion": "cleanup_and_return_to_base"}
```

Agent 拿到就知道：不要重试暂停，进入收尾。

### 原则 2：可预测接口

人类遇到模糊返回值会查日志、看上下文、试着重试；Agent 只能根据接口描述做分支。所以接口要满足：输入字段稳定、类型严格、单位明确；合法范围明确；输出状态可穷举；每个状态有稳定的 data 结构；错误不用隐式 exception 表达；降级不伪装成成功。

反例：

```json
move_to(target) → {"status": "failed", "message": "Something went wrong"}
```

Agent 不知道是越界、避障降级、控制权没释放，还是链路超时，四种处理方式完全不同。

正例：

```json
move_to(target) →
{
  "status": "rejected",
  "reason": "out_of_safe_zone",
  "recoverable": false,
  "suggestion": "skip_target_and_resume_route",
  "system_state": "route_paused"
}
```

`recoverable: false` 告诉它不能重试，`suggestion` 告诉它下一步，`system_state` 告诉它当前仍在可恢复状态。

### 原则 3：信息压缩

不要把原始数据扔过 Tool 边界。`read_raw_detections()` 返回 152 帧是反例；`list_unprocessed(only_when="stationary_confirmed")` 返回两个候选目标是正例。

### 原则 4：安全兜底，不可穿透

Agent 给出越界指令，不一定是它"错了"，可能是缺信息、prompt 没覆盖、或幻觉。无论原因，安全边界不能靠 Agent 自觉。它必须是 Runtime 或 Tool 契约里强制执行、Agent 无法绕过的硬约束。

```
Agent 调用 move_to(lat, lon, alt)
├── 安全区域检查 → out_of_safe_zone
├── 高度/距离检查 → movement_limit_exceeded
├── 电量检查 → low_power
├── 资源互斥检查 → route_still_running
├── 幂等检查 → target_already_processing
└── 全部通过 → 放行
```

尤其要避免三种假安全：静默修正（擅自把非法参数改成合法值但不告诉 Agent）、静默忽略（返回成功但没执行）、静默降级（用看似成功的状态掩盖失败）。

### 原则 5：循环必须可终止

任何自循环都要有预算：最大步数、token 上限、deadline、重复动作检测、失败升级。没有终止条件的"自愈"，只是把单步错误放大成系统性烧钱。

### 五平面：把"查了"和"改了"分开

五个平面是设计词汇，不是行业标准。控制面管生死，事件面管事实推送，状态面管现状快照，事实面管业务结果，安全面管动作合法性。它们分别对应 SDN 的控制面/数据面、云计算的管理面、ROS 的 Actions/Topics/Services/Parameters，但对应是类比，不是一一映射。

两个顺序性结论：

- **先订阅，再启动。** 先 `start()` 再 `on(event)`，启动后一毫秒内产生的事件会永久丢失。
- **状态查询三个不。** 不轮询等待业务结果、不猜测环境是否变化、不返回会改内部状态的"查询"。

判断设计有没有错，有一个简单测试：如果 Agent 在轮询 `status()` 来获取业务数据，说明事实面缺失；如果事实面里出现实时电量，说明状态面越界。

## 四、接口与代码

### 4.1 一个工具的完整契约

下面是一个抽象过的工具描述，字段名是本文约定，不是某个框架的官方 schema：

```json
{
  "name": "target_recognition",
  "intent": "在指定区域内发现并跟踪值得处理的目标",
  "state_machine": ["stopped", "running", "degraded"],
  "methods": {
    "start": {"from": ["stopped"], "to": "running", "returns": "handle"},
    "stop": {"from": ["running", "degraded"], "to": "stopped"},
    "list_unprocessed": {"side_effect": "none", "returns": "target[]"},
    "mark_processed": {"side_effect": "updates_target_lifecycle", "idempotent": true}
  },
  "events": ["on_detect", "on_target_lost", "on_degraded"],
  "safety": ["device_ready", "rate_limit", "power_ok"],
  "escape_hatch": "manual_observe"
}
```

契约要回答六件事：状态机、每个方法的合法前置状态、副作用、幂等性、事件、安全约束。缺一项就是设计缺口。

### 4.2 长任务与事件

长任务不能阻塞。`move_to(x,y)` 立即返回 `task_id`，完成通过事件推送，或由 Agent 调 `check_task_status(task_id)`。阻塞式调用会让循环卡在一步上，超时后模型重试，产生重复动作。

事件流不能写成轮询。每 0.5 秒查一次"有没有新目标"，既浪费上下文，也会漏事件：两个事件在间隔内同时发生，后一个覆盖前一个。

### 4.3 循环骨架

下面是伪代码，不是可直接运行的实现：

```
budget = {max_steps: 40, max_tokens: 200_000, deadline: now + 15min}
seen = set()
for step in range(budget.max_steps):
    if now > deadline or used_tokens > budget.max_tokens: break
    msg = await model.step(history, tools)
    if not msg.tool_calls: return msg
    for call in msg.tool_calls:
        key = hash(call.name, call.args)
        if key in seen:
            inject("duplicate action, stop and replan"); continue
        seen.add(key)
        result = await sandbox.execute(call, idempotency_key=key)
        history.append(tool_result(result))
```

关键不在代码，在省略不了的约束：最大步数防死循环；token 预算防烧钱；deadline 防长任务拖死会话；重复动作检测防反复试同一个失败调用；幂等键防重试导致重复副作用；检查点让崩溃后可恢复；终止条件要显式（任务完成、预算耗尽、连续 N 次无进展、人工取消、安全面拒绝）。

### 4.4 状态与事实分离

```json
// 状态面：易逝快照
get_status() → {"battery_pct": 18, "altitude_m": 50,
                "link": "fair", "flight_state": "cruising"}

// 事实面：持久结果
get_target("T-101") → {"type": "vehicle", "plate": "粤Bxxxx",
                        "confidence": 0.98, "evidence_path": "...",
                        "detected_at": "2026-10-24T09:12:31+08:00"}
```

电量、坐标下一秒就变；目标事实在任务结束后仍然有效。系统崩溃重启，状态面重置为 idle，事实面还在，Agent 可以接着干，不必重跑。

### 4.5 协议分层

Tools 是原子执行单元；Skills 是任务级能力；MCP 是连接协议。三者的关系是堆叠：基础设施（MCP/API）→ 执行单元（Tools）→ 解决方案（Skills）。

近似公式 **Skills = (Tools + Knowledge) × Reasoning** 说的不是数学，而是"只给工具不够"：工具解决"怎么做"，技能解决"做什么、用什么做、做到什么程度"。

工程上底层标准化 Tools（用 MCP 暴露），高层领域化 Skills（用 SOP、提示词、评测固化）。边界正在重叠——MCP 已能暴露 prompts 和 resources，Skills 也能打包成服务器——所以要明确治理归属：谁拥有工具描述、谁拥有编排逻辑、谁拥有权限。不回答，就会出现"工具在 MCP 层被放大权限、skill 在应用层绕过安全面"。

### 4.6 状态下沉的三条路线

推理层、云平台层、应用层各有代价（见表 4）。短期最现实的是组合：应用层管业务状态，厂商前缀缓存降成本，云平台管长期记忆。职责要写清楚：谁是 source of truth，谁只是缓存，谁负责遗忘与合规删除。否则会出现"应用层删了、云端还记得"的隐私事故。

## 五、反模式

| 反模式 | 一句话诊断 | 后果 |
|---|---|---|
| 薄 wrapper | 只是给原子 API 换个名字，内部没有状态机 | Agent 被迫管理一切 |
| Agent 帮 Tool 记状态 | Agent 记"我刚锁了目标"，而不是读真实状态 | 记忆与系统漂移，后续判断建立在错误假设上 |
| 失败只返 string | `{"status":"failed"}` 没有原因、可恢复性、建议 | Agent 只能猜，或盲目重试 |
| 隐式副作用 | 调 `mark_processed` 顺手释放资源锁，但没写 | Agent 以为还锁着，下一步报错 |
| 长任务伪装成同步 | `record_video(300)` 阻塞五分钟，没有 stop | 无法中断，超时后重复执行 |
| 事件流写成轮询 | 每 0.5 秒 `scan()` 一次 | 浪费上下文、漏事件 |
| 业务语义焊死 | "学校门口优先"写进识别 Tool | 换场景就要重写 Tool |
| 状态与事实混在一起 | 事实面里塞实时电量，状态面里查业务结果 | 幻觉执行、数据重复同步 |
| 小模型做大决策 | 端侧 4B 模型判断"是否上报、是否喊话" | 它给出看起来合理但不可靠的答案 |
| 自循环无终止 | 失败就重试，不设预算和重复检测 | 死循环烧钱，错误放大 |

反模式 1 的修法：内部封装完整生命周期——加锁、校验前置、处理中间失败、返回结构化结果。反模式 2 的修法：Tool 自己管理状态，Agent 每次决策前读状态，不靠记忆。反模式 3 的修法：每条错误携带 `reason`、`recoverable`、`suggestion`、`system_state`。

## 六、验证方式

### 6.1 端到端闭环

用一个完整工作流跑：启动 → 主循环 → 接收事件 → 处理中间失败 → 记录结果 → 恢复主流程 → 收尾 → 上报。重点看断裂点：中间失败后能不能恢复？结果能不能上报？中断后能不能接续？

### 6.2 场景切换

换一个业务场景，Tool 要不要改？需要大改，说明 Tool 里有业务语义泄漏；只需要换编排或加少量 Tool，设计合格。

### 6.3 失败路径完备性

随机选一个 Tool、一个状态、一个动作，问："如果这一步失败了，Agent 的下一步是什么？" Agent 能直接从返回结果拿到答案，而不是靠猜，设计合格。

### 6.4 评测阶梯

单元测试（函数级）→ 契约测试（工具输入输出）→ 端到端（真实链路）→ 语义评测（LLM-as-judge + 人抽检）→ 线上监控（逃逸率、回滚率）。每一层的通过都不能替代下一层。LLM-as-judge 只能做筛子，不能做终审，因为它和被测模型共享同类偏见。

### 6.5 反盲区设计

- **随机失败注入**：定期让某些门禁失败，或注入非确定性延迟，逼循环和人保持对异常的响应。
- **语义变更摘要**：即使全绿，也强制输出"这次变更改了什么行为"，附 diff 和测试结果，不能只给结论。
- **成对指标**：通过率必须和线上逃逸率一起看。逃逸率上升而通过率 100%，立即信任降级。
- **权限演练**：定期验证会话恢复是否作废授权、动态隐藏的工具是否真的调不到、MCP 是否在沙箱外。

## 七、Harness 自循环的风险，写透

harness 引导的工程自循环，指的是：模型生成变更 → harness 跑测试 → 失败则把错误喂回模型 → 修复 → 再跑，直到通过。它在局部确定性任务里非常有效，在复杂业务里有一组结构性风险。

**语义漂移。** harness 只能验证"代码是否符合规则"，不能验证"规则是否符合业务"。业务演进后，代码可以通过所有测试，却偏离用户期望。这是哥德尔式的缺口：系统内部无法自证其公理的正确性。

**过拟合 harness。** 自愈循环会寻找通过条件的最短路径。超时测试过不了就加盲目重试，性能测试过不了就缓存结果，安全测试过不了就吞掉异常。这些"修复"在测试环境完美，在高并发真机上引发雪崩。这是奖励黑客在工程层的翻版。

**mock 欺骗。** 复杂业务依赖大量外部系统，mock 往往静态、理想化。循环在 mock 里跑得越顺，与真实环境偏差越大。mock 覆盖率越高，越要配真实依赖的契约测试和混沌测试。

**上下文压缩丢信息。** 长任务必须压缩上下文，压缩算法一旦丢掉关键边际条件（某个必须在销毁前解绑的监听、某个特殊客户的白名单），模型就会做出错误决策。压缩是有损的，必须抽检：压缩前后对关键约束做一致性检查。

**权限与历史越权。** 会话恢复、fork、从日志恢复时，如果继承之前的授权，会出现"历史权限放大"。正确做法是恢复即作废一次性授权，重新申请。工具的动态隐藏也要双门禁：API 请求里不传该工具（前端门禁），运行时再拿 `tool_use_name` 与允许列表求交集（后端门禁），防止模型凭记忆调用已隐藏的工具。

**沙箱逃逸。** 内置 Bash 可以进沙箱（macOS Seatbelt、Linux bubblewrap），但第三方 MCP server 往往运行在宿主机，不受沙箱约束。模型可以通过给 MCP server 发指令，绕过沙箱执行任意动作。这是当前 Agent 安全最现实的盲区之一。对策是 MCP 来源白名单、MCP 独立沙箱、最小权限凭证、网络出口白名单。

**验证瓶颈。** 生成成本下降，验证成本不降。自循环产出的变更越多，人审队列越长。当人审成为瓶颈，团队会倾向于"相信门禁"，回到自动化偏见。

**自证的边界。** 自循环可靠的子域有明确特征：断言可穷举、mock 可覆盖、失败可回滚、语义可判定。编译器测试、算法题、单测生成、格式转换、Lean 证明属于这一类。开放业务、跨系统契约、物理控制、合规判断不属于。把后者塞进自循环，等于用有限规则给开放世界盖章。

一句话：harness 是脚手架，不是承重墙。它能把泥土聚拢，但钢筋要人埋。

## 八、情景推演

**基准情景（概率 55%）：工具层先成熟，harness 成为独立工种。**
触发条件：MCP 类协议成为事实标准；主流框架都支持有状态工具与流式 UI；评测仍以私有为主。
2029 年图景：工具设计从"写 API"变成"设计语义契约"，出现专门的 Agent 工具架构师岗位；封闭子域任务成功率 85%–90%，开放业务 60%–70%；状态管理以"应用层 + 前缀缓存 + 云记忆"混合为主。
验证指标：MCP server 数量与复用率；契约测试普及率；任务成功率与步数的相关性。

**乐观情景（概率 20%）：状态原生 + 协议统一，可靠性跨过 95%。**
触发条件：推理层原生支持可迁移会话状态；跨厂商状态标准出现；评测从静态题转向真实仓库与真实业务。
2029 年图景：Agent 跨会话、跨模型保持任务上下文；工具生态像 npm 一样可组合；harness 自循环在多数企业流程可用，人只做红区签字。
验证指标：跨模型状态迁移成功率；真实仓库任务成功率；Agent 引发的 P0 事故率。

**悲观情景（概率 25%）：碎片化与事故让 autonomy 收缩。**
触发条件：工具协议分裂；评测缺失导致"演示好、上线差"；出现由 MCP 或权限漏洞引发的重大事故。
2029 年图景：企业把 Agent 收回 Copilot 形态，只允许读和起草；harness 投入转向传统 CI/CD 与确定性自动化；工具设计回归"薄 wrapper + 人工编排"。
验证指标：Agent 项目留存率；权限相关事故数；企业 Agent 预算增速。

## 九、行动方案

**参考架构（自上而下）。**
接入层：统一输入（文本/语音/点击）→ 意图对象。
会话层：transcript、状态、预算、恢复。
执行层：queryLoop、工具分发、错误恢复。
工具层：五平面契约、有状态工具、结构化错误、幂等。
安全层：Deny-First 权限、模式状态机、OS 沙箱、凭证代理、MCP 隔离。
观测层：trace、token、工具成功率、逃逸率。

**迁移路径（三步）。**
第一步，2–4 周：盘点现有工具，标出"薄 wrapper"；给 3 个最高频的原子动作做有状态封装；建立契约测试。成功标准：这 3 个工具的端到端步数下降 50% 以上，错误自愈率上升。
第二步，1–2 个月：引入五平面，先做状态面与安全面；长任务改成 task_id + 事件；接入 trace。成功标准：幻觉执行归零；长任务超时率下降。
第三步，2–3 个月：加门禁与评测阶梯；接线上逃逸率；做 chaos 注入。成功标准：通过率与逃逸率同时可解释；P0 事故有归因。

**工具设计检查表。**
它完成的是原子动作还是原子意图？返回值是否带语义与置信度？失败是否结构化、可自愈？长任务是否非阻塞？是否幂等？是否标注只读/破坏性？是否经过安全面？是否有逃生舱？是否覆盖 90% 常见路径？

**门禁设计检查表。**
有没有独立 oracle？断言测的是行为还是指标？mock 与真实调用的比例是多少？压缩会不会丢关键约束？权限是否跨会话继承？MCP 是否在沙箱外？通过率与逃逸率是否成对？失败注入频率是多少？

**退出条件。**
任务成功率连续两周低于 70%；验证/生成时间比大于 2；出现一次由权限或 MCP 漏洞导致的安全事件；自循环连续 5 次不收敛且人工介入后仍无法定位。触发任一条，暂停 autonomy 扩张，回到人工确认模式。

## 十、风险与反方观点

**反方一：通用工具 + 更强模型会反超高阶工具。** 如果模型能可靠组合 50 个原子 API，高层封装就变成多余抽象。这个可能性存在，但受两条约束：步数乘法不会因为模型变强而消失（p 提升，n 仍在）；边缘情况的微操需求永远存在。更可能的终局是"高层工具做主干，原子工具做逃生舱"。

**反方二：五平面是过度设计。** 对内部 CRUD agent，五个平面的 runtime 与调试成本可能超过收益。同意。五平面适用于有物理约束、长任务、多系统协同的场景；简单场景用"工具 + 权限"两层就够。

**反方三：MCP 会吞掉 Skills。** MCP 已能暴露 prompts 和 resources，Skills 也能打包成服务器，边界确实模糊。但两者回答的问题不同：MCP 回答"能力如何被看见和调用"，Skills 回答"任务如何被完成"。吞掉的是"薄封装"，不是"任务能力"。

**反方四：状态下沉会导致厂商锁定。** 成立。缓解办法是把业务状态留在应用层，把 KV/缓存当作可丢弃的加速层；同时要求厂商提供状态导出。没有导出能力的原生状态，不应该成为 source of truth。

**反方五：可观测性与计费标准缺失。** 当前 trace 格式、按任务成功计费、跨 agent 调用链都没有共识。后果是故障无法归因、ROI 无法计算。短期只能用私有标准 + OpenTelemetry 兼容层过渡。

**反方六：harness 的数字都不可核对。** "80% 是 harness""51 万行""1902 个文件""utils 35.2%"都来自第三方逆向或用户贴入的材料，版本、口径、统计方法不透明；同一批材料里还出现过约 16 万行与 51 万行两种说法。本文只用它们做方向性说明，不当作事实基准。真正可核对的是行为：权限是否 Deny-First、沙箱是否用 OS primitive、会话恢复是否作废授权、工具是否返回 diff。

## 十一、跟踪指标与触发规则

| 指标 | 口径 | 目标/阈值 | 触发动作 |
|---|---|---|---|
| 任务级成功率 | 端到端通过验收 | 封闭子域 ≥90%，开放业务 ≥70% | 低于阈值缩任务粒度 |
| 平均步数 | 每任务工具调用次数 | 同比下降 30% | 不降反升，检查工具抽象 |
| 人工介入率 | 需打断/接管的任务占比 | <30% | >50% 停扩 autonomy |
| 线上逃逸率 | 门禁过但线上故障 | 连续 2 周不上升 | 上升即信任降级 |
| 工具错误自愈率 | 结构化错误后重试成功占比 | >60% | 低于阈值改错误契约 |
| 每任务 token 成本 | 含重试与压缩 | 环比不增 | 增则查循环与上下文 |
| 压缩丢失率 | 抽检发现关键约束丢失的比例 | <2% | 超标改压缩策略 |
| 权限弹窗率 | 每任务人工确认次数 | 稳定或下降 | 上升查 Deny 规则粒度 |
| p95 首 token 延迟 | 从请求到首字 | <2s | 超标查状态与检索 |
| 安全事件数 | 权限/MCP/沙箱相关 | 0 | 任一事件全量复盘 |

规则示例：线上逃逸率连续两周上升，且门禁通过率高于 95%，自动把所有黄区任务降为红区，直到逃逸率回落；工具错误自愈率低于 40%，暂停该工具的自循环，改为人审。

## 事实核查与批判性审查

> 本节逐条核查报告所依赖的关键说法。判定标准：只抓硬事实（日期、人物、定义、公式、单位、换算、算术、来源、A 当 B）；预测未兑现、数据截至某时点、观点分歧不算错误。

### 核查范围与方法

- **第三方逆向数字**：Claude Code 的代码行数、文件数、版本号、模块占比，追溯原始材料与统计口径。
- **API 与版本归属**：`UIMessage`、`convertToModelMessages`、`toUIMessageStreamResponse` 属于哪个 SDK 版本。
- **技术机制表述**：无状态 API 与 KV Cache 的关系、prompt caching 的可复用范围。
- **名称与分类**：Superpower 是什么、A-IaaS/A-PaaS/AaaS 是否行业通用命名、五平面是不是现成标准。
- **安全事项**：材料中是否含明文凭据、MCP 是否在沙箱外。
- **经验倍数**：token 消耗 3–5 倍、低于 70B 会死循环等，检查有无测量口径。

交叉核对方式：官方 SDK 文档、源文章原文比对、产品行为观察；无法核对的行数/占比一律降为方向性参考。证据等级：A=原始披露或权威指南；B=多源一致；C=单一来源；D=推算或待核实。

### 待核实与证据边界

- **第三方逆向的代码规模、文件数、模块占比**：无法独立核对，版本、统计口径、是否含生成代码都不清楚。对结论的影响是次要的——本文的架构论证不依赖这些数字。
- **Superpowers token 3–5 倍、低于 70B 死循环**：属经验估计，缺任务类型、上下文长度、缓存命中率。只能用于提醒“技能树有成本”，不能用于容量规划。
- **明文 API Key**：安全事项，不是分析结论。归档文件不应公开分发；密钥是否仍有效需在供应商侧确认。
- **五平面的行业地位**：组件来源可核对，但“五平面”作为整体不是标准；文中已把它定义为设计词汇。
- **MCP 运行在宿主机、可绕过沙箱**：这是对当前实现的观察，随客户端版本变化；具体攻击面需要按版本验证。
- **“任务成功率可以差出数倍”**：方向性判断，缺同一模型、同一任务集的对照实验。

### 对报告结论的影响

- **KV Cache 修正直接改写结论 5**：原来说“无状态 API 迫使应用层手动拼 prompt 模拟状态”，修正后要区分两层——厂商前缀缓存已经解决了 KV 复用，真正缺的是应用自定义状态的承载。这让“状态管理是最大工程债”的论点更精确：债不在 KV，而在业务状态、事实面与恢复语义。
- **35% 误读修正削弱了“上下文管理占比最高”的量化支撑**：结论 5 仍成立，但依据从“代码占比”退回“接口设计缺口”；读者不应再用 35.2% 论证上下文管理的重要性。
- **AI SDK 版本修正只影响示例与附录**：不影响工具契约、五平面、循环预算等主体结论；但会让照抄代码的人踩版本坑。
- **API Key 是分发风险，不是分析错误**：不改变任何结论，但改变这份文档能否公开；处理优先级高于所有技术修正。
- **Superpower 分类修正只影响术语**：结论 4（Tools/Skills/MCP 三层）不依赖 Superpower 的定性；把技能库误称“方法论/范式”会误导读者以为它是模型层创新。
- **五平面与 A-IaaS 的限定影响结论 3 的适用方式**：五平面可以作为设计检查表，但不能声称“业界标准”；读者若要落地，需要自己验证五个平面是否匹配场景，简单 CRUD agent 用两层就够。
- **第三方数字全部降级后，关于 Claude Code 的所有定量比较都应打折**：行数、占比、版本号不能用于“谁更强”的论证；可保留的是可观察行为——Deny-First 权限、OS 沙箱、会话恢复作废授权、工具返回 diff。
- **需要打折的结论**：Superpowers 的成本倍数、技能树规模阈值、MCP 沙箱风险的普遍性，都是经验判断；相对稳健的是接口层结论——pⁿ 衰减、状态面/事实面分离、循环必须有预算与终止条件、降级不能伪装成功。
