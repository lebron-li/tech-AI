# Coding 先落地，不是因为代码数据多：Agent 的边界由五个可测变量决定

> 一家公司把 coding agent 的成功经验原样搬到无人机运维和企业 ERP，三个月后项目回到原点。同样的模型，为什么换一个场景就不灵？

## 引子：同一套 Agent，换个场景就不灵

下面是一个复合场景，公司与数字为示意，机制来自多个真实项目的共性。

一家公司的研发团队用 coding agent 效果很好：单元测试通过率上去了，重构速度翻倍，工程师愿意把重复劳动交出去。管理层很自然地想：既然代码能自动化，运维和业务也能。

第一个试点是无人机巡检。团队把设备的两百多个原子 API 文档丢给 Agent，让它自己编排"起飞—巡检—识别—取证—返航"。演示很顺利：五步任务，每一步都成功。上线后问题来了：风一大，云台锁定的目标就丢；`move_to` 超时后 Agent 重试，设备已经偏离航线；电池到 20% 时 Agent 还在执行"再拍一张"；一次误判让设备在禁飞区边缘悬停了两分钟。每一步接口都返回 `ok`，整体却不可用。

第二个试点是 ERP 流程。团队想让 Agent 自动处理采购申请：读需求、查库存、比价、生成采购单、送审批。接口打通花了六周，Agent 能跑通演示。真实业务里，采购员还要考虑"这家供应商是老板的关系户""这个部门今年的预算不能超""这批货虽然便宜但交期赶不上促销"。这些信息不在系统里，Agent 生成的"最优方案"在政治上不可行。项目最后退回成"帮用户起草采购单"。

两次失败不是因为模型不够强，而是因为团队把"coding 的成功"当成了"Agent 的成功"。Coding 有一组别的领域没有的条件：形式化的知识、独立的编译器 oracle、零成本的 git 回滚、毫秒级的反馈。离开这四个条件，同一套方法就会失效。

这篇文章回答：**Agent 的落地边界在哪里，用什么变量判断，边界内怎么做，边界外怎么退。**

## 核心结论

1. **Coding 率先落地，是五个条件同时成立的乘积结果，不是"代码语料多"这一条。** 五个变量是可观测性 O、可验证性 V、可逆性 R、符号同构性 T、反馈延迟与采样成本 L。Coding 在五项上接近物理极限；医疗、法律、金融、物联网至少缺两到四项。

2. **"知识—环境—纠错"三元组是这套框架的简化版，只覆盖数字世界。** 它能解释代码，解释不了物理设备的惯性、组织里的隐性知识、部门之间的利益博弈。把三元组当普适定律，会得出"把一切业务代码化就能自动化"的错误结论。

3. **物联网与物理设备在 3–5 年内实现端到端自主化的概率，我估计在 20%–30%。** 瓶颈不是模型不够聪明，而是部分可观测（POMDP）、物理不可逆、Sim-to-Real 落差，以及"API 返回 200 但阀门没动"的虚假成功。

4. **Coding 内部同样分层。** 同一模型在无状态纯函数上约 10 倍提效，在机械重构上 5–10 倍，在跨系统链路排错和十八层 if-else 的业务补丁上是负收益，最差可到 -50%。"AI 编程"不是一个均匀的能力，而是一张收益矩阵。

5. **组织不被提效，主要卡在 W = E + C 里的 C，而不是 E。** Agent 把执行耗时 E 压掉 80%，协调耗时 C 可能一点没降。C 在知识工作里占多大比例没有统一测量，但多数企业的经验值在 50%–70% 区间；只要 C 不动，总工时就近似不动，还会因为产出变多而触发"组织版阿姆达尔定律"和杰文斯悖论。

6. **Spec Coding 的本质是把认知负荷前置，不是让文档替代代码。** 它适合绿地项目、微服务、已有 TDD 习惯的团队；在遗留系统上，它必须先变成"防腐层 + 特征测试 + 绞杀者替换"的三段工程，否则会把看不见的副作用一起重写掉。6 个月接管 30% 高频变更路径是合理预期，不是承诺。

7. **Harness 引导的自循环只在"断言可穷举、mock 可覆盖"的子域可靠。** 流程本身不完善时，一连串绿色门禁必然降低人的警觉，这是自动化偏见的稳定结论，不是偶发现象。门禁必须配反盲区设计：随机失败注入、语义变更摘要、线上逃逸率与通过率成对考核。

8. **可操作的判断标准是一张五问评分卡。** 独立 oracle、失败可逆、产物同构、单步成功率与步数、协调成本占比，五项各 0–2 分；8 分以上直接上，5–7 分做试点，4 分以下不要用 Agent 接管主流程。

## 问题与分析框架

### 五个变量，而不是三个

把 Agent 能否落地拆成五个可观察的量，比"知识—环境—纠错"更好用，因为每一项都能在项目开始前打分。

**可观测性 O（Observability）。** 环境状态能否被无损读取。代码世界的状态是 AST、内存、日志、退出码，可以 100% 读取；物理世界只有温度、电压、振动、图像这些稀疏采样，大量隐变量（摩擦系数、金属疲劳、网络抖动）不可见。O 低，模型只能在不完全信息下决策。

**可验证性 V（Verifiability）。** 是否存在独立于模型自身、毫秒级给出对错的 oracle。编译器、类型检查器、单元测试、Lean 4 的证明检查器都是。法律没有"裁判编译器"，医疗没有"生理反应编译器"，金融的回测会被市场反身性污染。V 低，强化学习就没有可靠奖励，模型只能靠人打分。

**可逆性 R（Reversibility）。** 失败能否低成本回滚。`git reset --hard` 是零成本；容器删了重建是分钟级；阀门超压爆管、手术并发症、错单穿仓不可逆。R 决定系统敢不敢让 Agent 探索。R 低的领域，试错次数被物理规律锁死，样本量永远不够。

**符号同构性 T（Token–Artifact Isomorphism）。** 模型输出的符号，是否就是最终产物。代码是"所想即所得"：生成的文本编译通过，软件就已经存在。无人机的 JSON 指令不等于机械臂抓到了物体；诊疗方案不等于患者指标改善。T 低，中间隔着一段物理或社会过程，模型无法直接为结果负责。

**反馈延迟与采样成本 L（Feedback Latency & Sample Cost）。** 从动作到拿到奖励信号的时间和钱。代码是毫秒到分钟；药物疗效是数月到数年；组织决策的反馈要以季度计。L 高，单位时间内能积累的样本极少，任何"试错学习"都变成奢侈品。

一个领域的适配度不是五项相加，而是相乘。任何一项接近零，整体就接近零。这就是为什么"模型再强一点"不能自动解决医疗和 IoT：强的是推理，不是 oracle，也不是可逆性。

### 可靠性是乘法

设一个任务要 n 步，每步成功率 p，则端到端成功率近似为：

**Success ≈ ∏ᵢ P(stepᵢ) = pⁿ**

n=50、p=0.99 时，成功率约 60.5%；p=0.95 时只剩 7.7%。这条公式解释了两件事：第一，为什么把 50 个原子 API 合成 5 个高层工具，比换一个更聪明的模型更有效；第二，为什么"演示很惊艳、上线就崩"——演示通常只有 5 步，生产链路有 50 步。

它也解释了 Coding 的优势：编译器和测试把每一步的 p 拉得很高，git 让失败不进入下一步，所以 n 可以大、p 可以高。物理世界恰好相反：n 大、p 低、失败还不可撤销。

### 总工时 W = E + C

把知识工作者的时间拆成执行 E（写代码、做表、写方案）和协调 C（对齐、审批、会议、信任建立、责任划分）。Agent 直接压缩的是 E。C 是否下降，取决于三件事：信息是否可被 Agent 读取、接口是否标准化、责任是否可转移。

C 不降时，会出现两个效应。**组织版阿姆达尔定律**：系统吞吐由最慢的未加速环节决定，E 加速 10 倍，总吞吐最多提升到 C 的边界。**杰文斯悖论**：生成成本下降，中间产物（方案、报告、原型）数量爆炸，需要人来评审和对齐的接口反而变多，总工时可能上升。

### 语义鸿沟

复杂业务是开放、高熵、非线性的；harness 是封闭、低熵、有限状态的。harness 的断言来自人类已有认知，是对现实的一次降维剪裁。用剪裁过的规则去完全控制未剪裁的现实，中间那条缝就是语义鸿沟。它不是工程做得不够好，而是"用有限规则描述开放世界"的固有缺口。哥德尔不完备定理和 Ashby 的必要多样性定律说的是同一件事：控制器的复杂度不能低于被控系统。

## 四条路径对比

确认"这个领域不适合端到端 Agent"之后，不是只能放弃。有四条路，成本和收益完全不同。

**路径 A：通用 Agent 直接接管。** 把 API 文档丢给模型，让它自由编排。成本最低，演示最快；但对 O/V/R 低的领域，成功率会随步骤数指数衰减，物理领域还可能出事故。只适合幂等、可验证、可回滚的数字任务。

**路径 B：Copilot 辅助。** Agent 只做检索、起草、找茬，最终动作由人执行。可靠性高，责任清晰；天花板也低，提效集中在"信息处理"而不是"执行"。适合医疗、法律、金融等 R 低但信息量大的领域。

**路径 C：先建 oracle，再逐步放开。** 先补测试、快照、契约、仿真，把 V 和 R 拉起来，再让 Agent 接管。前期投入大、见效慢；但它是遗留系统和高风险领域唯一可持续的路径。Coding 的遗留系统改造、工业的数字孪生都属于这一类。

**路径 D：改造业务，使其可验证。** 把流程拆成状态机、把规则写成可执行契约、把接口标准化。这是"让领域向 Agent 靠拢"，周期最长，但一旦建成，复用性最高。亚马逊的 API Mandate 是成功样本，OGAS 是失败样本。

**表 4：四条路径的选择**

| 路径 | 前期成本 | 提效上限 | 风险 | 适用条件 |
|---|---|---|---|---|
| A 通用 Agent | 低 | 高（理论上） | 高 | O/V/R 都高、失败可回滚 |
| B Copilot | 低 | 中 | 低 | 信息密集、责任不可转移 |
| C 先建 oracle | 中高 | 高 | 中 | 有明确验证标准、可局部改造 |
| D 改造业务 | 很高 | 很高 | 中高 | 有强权威、长期投入、接口可标准化 |

推荐顺序是 C → B → D → A，而不是反过来。先建可验证的局部，再扩大到辅助，再改造边界，最后才谈自主。跳过 C 直接做 A，是多数失败项目的共同路径。

## 证据与论证

### 一、Coding 的三重闭环，缺一不可

**符号同构。** 代码既是模型的思考媒介，也是最终交付物。模型输出一段文本，编译通过、测试通过，生产力成果已经在数字空间完成交割。没有"想完了还要落到物理世界"的最后一公里。

**外部 oracle。** 语法与类型检查在运行前拦截低级错误；单元测试给出二值断言；Lean 4、Isabelle、Dafny 把正确性从"样例覆盖"提升到"逻辑证明"。关键点在于 oracle 独立于模型：用 LLM 评 LLM 只会放大自我确认偏见，用编译器评 LLM 才有客观标准。

**零成本回滚。** Docker 里 `rm -rf /` 的破坏力为零；`git reset --hard` 瞬间恢复；分支让 Agent 可以并行探索上万次，通过全部回归测试才合并。试错在代码世界里不仅安全，还是获取知识的主要方式。

三者合起来，才支撑了基于执行反馈的强化学习（RLEF）和基于可验证奖励的强化学习（RLVR）。一个可用的功能正确性奖励可以写成：

- 原来失败、现在通过（功能升级）：+1.0
- 原来通过、现在仍通过（维持）：+0.5
- 原来失败、现在仍失败（维持失败）：-0.5
- 原来通过、现在失败（功能降级）：-1.0

这个奖励完全不需要人工标注，可以自动算。医疗、法律、金融找不到对应的标量。这就是"为什么 RLVR 先在代码和数学爆发"的算术原因。

**但这个闭环有前提：测试存在且可信。** 在无测试覆盖的遗留系统里，oracle 消失，R 下降，三重闭环同时瓦解。所以"coding 已落地"准确的说法是"有测试的 coding 已落地"。

### 二、Coding 内部的分层：能力方差来自上下文耦合

巨石应用维护是观察 AI 能力边界的天然实验场。高收益区有三个共同点：输入输出可枚举、不依赖项目潜规则、失败可局部验证。负收益区也有三个共同点：跨模块副作用、隐性架构约定、根因在视野之外。

具体机制值得展开。修改一个被几十个模块引用的公共函数，AI 通过索引看到的只是调用点，看不到运行时才会暴露的蝴蝶效应；它修好当前 Bug，可能让另外三个页面回归。祖传架构里的"必须在 beforeDestroy 手动解绑全局监听"这类潜规则，不在训练语料里，也不在 README 里，模型会按标准方案重写，代码看起来更干净，跑起来全是坑。十八层 if-else 背后是多年的业务妥协，模型不知道哪一层是防御性编程，会把"冗余"删掉——这正是切斯特顿栅栏的反面教材：看见一道栅栏，不知道为何而立，就不该拆。

可操作的用法不是"让 AI 少写代码"，而是重新切分任务：

- 手动指定 3–5 个相关文件，做上下文的过滤器，不把整个仓库丢进去；
- 只让它写纯函数，调用点由人接；
- 把它当对立面，问"这段代码在什么极端情况下会报错""有没有内存泄漏"，找茬能力通常强于写复杂业务的能力。

一句话：把 AI 当局部战术武器，不做战略决策。

### 三、物理世界：为什么 IoT 比医疗还难

IoT 的困难是叠加的，不是单点的。

**部分可观测。** 代码状态可以全量读；物理设备的状态受温度、湿度、电压、机械磨损影响，传感器只给你稀疏、有噪的采样。同一个"上升 10 米"指令，在阵风、低电量、GPS 漂移下有不同的物理后果。这是标准的 POMDP，不是"上下文不够长"。

**API 虚假成功。** 云端收到 HTTP 200，只代表指令到了网关，不代表阀门关了、机械臂到了位。阀门可能锈死，电机可能堵转。没有高密度反向传感器，Agent 的执行本质是开环。更危险的是，这个 200 会被模型当成"已完成"，进入下一步。

**物理不可逆。** 代码删库可以恢复，超压爆管、机械臂碰撞、无人机坠机不能。R 接近零，意味着不能靠试错学习，只能靠预演。

**时间尺度不对等。** 编译是毫秒，温控、阀门、机械运动有惯性和分钟级滞后。单位时间内拿不到足够样本，RL 的样本效率假设失效。

**Sim-to-Real 落差。** 数字孪生可以跑一百万次，但摩擦系数突变、传感器漂移、突发断电这些"长尾物理"，仿真里没有。仿真里越完美，真机上越脆弱。

**本体（ontology）救不了。** 本体是"概念字典 + 规则手册"，能统一命名（PLC 里的 Dev_A03_Temp、维修日志里的"1 号锅炉温度"、ERP 里的 Asset_9982 是同一个东西），能拦非法指令（3 号阀门耐压 80，拒绝 100），能把老师傅的因果链写成规则。但它有四个硬限制：大量 know-how 是感官的、意会的，翻译成"如果……就……"会丢细节（波兰尼悖论）；本体是静态说明书，不是练习沙箱；现实一变就要人工维护，维护成本可能高于直接用人；遇到规则库没写过的未知未知，系统不会优雅降级，会死锁。

**正确的落地姿势是分层，不是端到端。** 大模型只做高层规划（"把 A 产线今天能耗降 5%"），本体做安全审查，PID/PLC 做底层执行。Agent 不直接碰物理开关。这个架构不性感，但它是目前唯一能把事故率压到可接受范围的做法。

### 四、组织世界：C 为什么压不下去

企业没有为 Agent 准备好基础设施，这句话可以拆成三层阻尼。

**数字基础设施阻尼。** 财务的"营收"、销售的"流水"、供应链的"交付"不是同一个口径；核心流程散落在钉钉、企微、Excel 和私人聊天里；ERP、CRM、OA 之间没有统一 API。Agent 无法像调用 Terminal 一样跨系统游走。要让它能走，先要花极高成本做接口封装和数据清洗。

**信息暗物质阻尼。** 企业不是按 SOP 运行的，是按隐性知识和社会资本运行的。"这个方案理论上可行，但找 A 部门审批一定挂，因为 A 部门今年指标不在这里；得找 B 部门的 C 哥，换个名义推进。"这类信息不进 Wiki，只在茶水间流动。信任也是不可 Token 化的资产：推进高风险事情靠的不是方案完美，而是有人愿意用职业生涯背书。Agent 只有智商，没有社会身份，无法做信任抵押。

**激励阻尼。** 中层管理者的理性选择是风险最小化：不干活的风险是 0，用 AI 搞创新出 Bug 的风险是 100。Agent 越聪明、产出越快，越容易被组织视为失控源。部门墙同样：信息不对称是很多岗位的护城河，要求打通数据等于要求交出控制权。

在此之上还有四个放大器。

**验证瓶颈。** 生成成本趋近于零，验证成本趋近于无穷。一份 30 页、逻辑通顺、数据可疑的报告，专家要逐条核对，花的时间可能超过自己写。信息稀缺时代生产是瓶颈，AI 时代验证是瓶颈。当组织里充满"看起来专业但细节不可靠"的产出，决策者的认知资源会被"鉴毒"耗尽。

**帕金森定律的 AI 变体。** 原来 5 页的汇报，因为 AI 做得快，变成 50 页加 3 个预案；上级觉得有责任认真看，于是会开得更长。下属用 AI 生成方案，领导用 AI 生成意见，两个模型在文档里打架，人在会上照本宣科。AI 没有消除冗余，只是把冗余合法化、规模化。

**局部优化。** 企业引入 AI 的方式常常是"给旧流程贴补丁"：本来不该存在的跨部门周报，现在用 AI 自动生成；本来繁琐的审批，现在用 AI 帮员工写理由。用极高的效率做本就不该做的事，是生产力最大的黑洞。蒸汽机发明后，工厂花了数十年重排布局才真正提效；只给马车换引擎，不会得到火车。

**人才再生产断层。** 高手是从几千次低精度体力活里长出来的：写单测、查简单 API Bug、洗脏数据。AI 接管这些活之后，初级员工失去成长阶梯；等老一代退休，新一代没有底层的"手感"，也就没有识别 AI 胡说八道的能力。这是用未来储备换当下效率。

**测量 observer effect。** 当考核指标附带严厉奖惩，被考核者会主动污染数据源：隐瞒缺陷、私下修 Bug 不录入、把高难度任务写成低难度描述。管理层和 AI 收到的都是美化过的遥测，组织在虚假数据里失明。

一个具体的制度样本是"AI 评工分 + Bug 溯源到人 + 任务原子化"。它的演化路径几乎是确定的：Jira 描述变成作文大赛，老实干活的人拿低分，会写 Prompt 的人拿高分（古德哈特定律）；Bug 追责让所有人不敢重构、不敢碰历史代码，宁可 Copy-Paste 也不抽象（防御性工程）；任务切成单人单 Jira，模块缝隙里的联调、兼容、垫后工作没人拿分（三不管地带）；校招生去萃取老专家经验，只能拿到 30% 的显性规则，剩下 70% 涉及渠道关系、战略客户、供应商博弈，既问不出也写不进代码。最后系统退化成"上百个下拉框的超级 Excel"，工程师沦为"肉体 API"和背锅中介。

### 五、组织能否被代码化：四个案例的分界线

OGAS 失败，不是因为计算机不够强，而是因为它试图用一个封闭的、可枚举的模型去表达一个开放的、充满博弈的现实。基层为了完成"以吨计重"的指标虚报数据，系统算出的最优调配与现实物资短缺完全脱节。这是"状态空间不可压缩"的教科书案例。

亚马逊 API Mandate 成功，是因为它只规定边界：所有团队必须通过服务接口暴露数据与功能，禁止私下对接和直连数据库；它不规定团队内部怎么实现、怎么排期、怎么考核。只管接口，不管实现；在组织边界上强制，在边界内自治。这是可迁移的原则。

微软 stack ranking 失败，是因为它量化的是人，不是接口。强制排名把同事变成对手，把合作变成零和，把"多做多错"写进制度。需要修正一个常见的时间线错误：这套制度是在 2013 年 11 月由时任 CEO 史蒂夫·鲍尔默宣布废除的，不是"纳德拉上台后才废除"；纳德拉 2014 年 2 月才接任。

桥水 Dot Collector 是一个极端实验：把员工的思维、性格、决策直觉量化成实时点数，按历史可信度加权。它在达利欧的个人权威下维持运转，但组织摩擦和人才流失很高。公开报道常提"近三分之一新人前两年离职"，这个数字缺少可核对的分母口径，只能当量级参考。它说明的是：测量本身会改变行为，而靠强人权威压制的测量，很难在权威退场后存活。

四个案例给出同一条线：**可以代码化的是接口、契约、状态机；难以代码化的是人的判断、信任、利益和未定义边缘。** 越过这条线，系统会从"高效"直接跳到"脆弱"。

### 六、可操作的判断标准

在立项前问五个问题，每个 0–2 分。

1. **有没有独立 oracle？** 能否在 1 分钟内、不依赖模型自身，给出 pass/fail。编译器、单测、形式化检查器算 2 分；只有人工评审算 0–1 分。
2. **失败可逆吗？** 回滚成本是否显著低于重做成本。git/容器 2 分；需要停机、赔偿、手术 0 分。
3. **产物与思考同构吗？** 模型输出的符号是否就是交付物。代码、SQL、配置 2 分；需要物理执行或人际谈判 0 分。
4. **单步成功率 × 步数能过线吗？** 估算 p 和 n，pⁿ 是否大于 80%。过线 2 分，60%–80% 给 1 分。
5. **协调成本占比低于 30% 吗？** 如果需要跨三个以上部门、依赖隐性知识、责任无法转移，给 0 分。

8 分以上：可以让 Agent 接管主流程，人做抽查。5–7 分：做 Copilot 或局部自动化试点，保留人工确认。4 分以下：不要让它碰主流程，最多做检索、草稿、找茬。

人的介入点也应该固定在三处，而不是随机救火：**元规则变更**（商业模式、跨系统契约变了，要重写断言）、**边界外异常**（连续修复 N 次仍不通过，或出现 harness 没覆盖的黑天鹅）、**非确定性语义审查**（涉及合规、资金、人身安全，或代码能跑但架构熵过高）。

## 反模式：边界判断的常见错误

| 反模式 | 表现 | 为什么错 | 修法 |
|---|---|---|---|
| 用数据量解释一切 | "代码数据多，所以 coding 先落地" | 医疗文本也不少，法律文书更多；缺的是 oracle 和可逆性 | 用五维评分而非语料规模 |
| 把演示当生产 | 五步 demo 跑通就立项 | 成功率随步数指数衰减，50 步后可能只剩 60% | 按真实链路步数做压力测试 |
| 用更强模型替代接口改造 | 每次失败都归因"模型不够聪明" | 模型提升单步 p，不降低 n，不解决不可逆 | 先合并工具、补 oracle、加回滚 |
| 把组织问题当技术问题 | 上 Agent 解决跨部门协调 | W=E+C，C 不动，总工时不降 | 先改接口与责任，再谈自动化 |
| 用量化指标管理人 | 工分制、Bug 溯源、AI 评 Jira | 指标变目标即失效，诱发防御性行为 | 量化接口，不量化人 |
| 把一切业务代码化 | 认为规则足够细就能覆盖现实 | 开放世界有未知未知，形式系统会死锁 | 分层治理，保留人工裁量与逃生舱 |
| 无测试就上自愈 | 让 Agent 自动改遗留核心代码 | 没有 oracle，自循环等于蒙眼狂奔 | 先建特征测试与快照 |
| 忽视隐性知识 | 认为文档化就能交接 | 大量 know-how 是感官的、关系的 | 人机分工，Agent 做显性部分 |

其中最危险的是"把组织问题当技术问题"。它会让项目在技术上成功、在业务上失败：Agent 确实生成了更多方案、更快地跑了流程，但评审、对齐、签字的工作量同步上升，管理层看不到总工时的下降，最后得出"AI 没用"的结论。真实原因不是 AI 没用，是只优化了 E 而没有动 C。

## 验证方式

### 小样本压力测试

选 20 个真实任务，不用 demo 数据。记录四个数：端到端成功率、平均步数、人工介入次数、失败后的恢复时间。真实任务要包含脏数据、权限冲突、超长附件、异常网络，这些才是生产环境的主体。

### 反事实对照

同一批任务，一组用 Agent，一组不用，比较总工时而不是生成时间。总工时包括生成、验证、返工、协调。只比生成时间，会得出"提效 10 倍"的错觉。

### 边界回归测试

每月挑一个"当前认为不适合"的领域，用五维评分重跑一次。模型能力在变，边界会移动；不重跑，判断会过期。反过来，也要挑一个"当前认为适合"的领域，检查是否出现了新的失败模式。

### 组织指标

除了任务指标，还要看三个组织指标：验证/生成时间比、线上逃逸率、新人独立交付周期。前两个衡量"AI 产出是否被消化"，第三个衡量"人才 pipeline 是否被透支"。

## 情景推演

**基准情景（概率 55%）：Coding 继续加深，其他领域分层渗透。**
触发条件：模型能力按现有曲线提升，编译器/测试/oracle 体系不变，企业接口标准化缓慢推进。
2029 年图景：Coding Agent 从"写函数"扩展到"有测试覆盖的模块级重构"，遗留系统仍以人为主导；企业流程在客服、报表、审批草稿等低风险环节普及，跨部门主流程变化不大；IoT 在巡检、安防、农业等"人在回路"场景规模化，端到端自主仍受限。
验证指标：SWE-bench 类基准与真实仓库成功率的差距是否缩小；企业 Agent 项目的 ROI 是否转正；IoT 事故率是否随部署量线性上升。

**乐观情景（概率 20%）：世界模型与数字孪生把 IoT 的 R 和 T 拉起来。**
触发条件：高保真物理引擎 + 世界模型把 Sim-to-Real 落差压到可接受范围；传感器成本下降，反向校验密度上来；行业出现可复用的安全认证标准。
2029 年图景：IoT 自主化概率从 20%–30% 升到 40%–50%，但仍以"带限自主"为主——Agent 做高层规划，底层由确定性控制器兜底。企业流程因 MCP 类协议普及而明显打通，C 开始下降。
验证指标：数字孪生与真机的策略迁移成功率；单台设备的传感器密度与成本；行业安全认证的落地数量。

**悲观情景（概率 25%）：验证瓶颈与组织摩擦让 ROI 不达标，投资回撤。**
触发条件：Agent 产出量增速远超人的验证能力；出现若干起由 Agent 引发的重大事故；企业发现"AI 提效"只体现在生成量，不体现在交付周期。
2029 年图景：大量 Agent 项目从"自主"退回"辅助"，预算向确定性自动化（RPA、规则引擎）回摆；Coding 仍是最大市场，但增速放缓；组织对 Agent 的信任进入"一次事故、长期收紧"的周期。
验证指标：Agent 项目的留存率；线上逃逸率；因 AI 产出导致的返工工时占比；企业 Agent 预算的同比增速。

三个情景的概率之和为 100%。分歧点不在模型智商，而在 V 和 R 能否被工程手段改善。

## 行动方案

**个人工程师（优先级从高到低）。**
第一，用五问评分卡给自己的任务分类，只在高分任务上放开 autonomy，低分任务只用来找茬和起草。
第二，先建 oracle 再用 Agent：写单测、写快照、写类型约束，验证网没建好之前不要让 AI 改核心链路。
第三，坚持"纯函数给 AI、调用点给人"的边界，尤其在巨石应用里。
第四，记录"验证时间 / 生成时间"的比值。这个比值超过 2，说明这类任务不适合再交给 Agent。
退出条件：连续两周出现 AI 引入的回归，或验证时间超过自己重写的时间，就停用该类任务。

**团队（遗留系统改造，6 个月）。**
0–1 个月：止血与测绘。禁止 AI 直接改旧核心代码；新需求走防腐层；用流量录制工具（GoReplay、JVM-Sandbox 一类）抓真实 I/O，让 AI 生成黑盒快照测试。
1–3 个月：圈地。找无状态叶子节点（纯计算、工具类、ETL）做试点；人读旧代码提炼规则，人写 Spec，AI 先写测试、人审测试、AI 再写实现；跑通快照后废弃旧代码。
3–6 个月：接管高频路径。用"功能核心/命令式外壳"把纯逻辑与数据库、外部 API 隔开；CI 里加硬拦截，PR 与 Spec 不一致直接拒绝。
预期：6 个月接管约 30% 的高频变更路径，剩余 70% 稳定但无人敢动的代码封存。这个 30% 是工程推演，不是实测统计。
止损条件：头两个月交付速度下降超过 40% 且没有 CTO 级背书，项目会被叫停；这时应缩回单模块试点，而不是全面铺开。

**企业（组织层）。**
第一，学 API Mandate，不学工分制：强制接口标准化，不量化人。
第二，按风险分三区：绿区（测试数据、低额退款、样式修复）全自主；黄区（对外邮件、非核心发布）先执行后 24 小时内抽样；红区（转账、核心库、权限变更）只允许 Agent 出方案和仿真，人输入密钥执行。
第三，门禁成对考核：通过率必须和线上逃逸率一起看；逃逸率上升而通过率 100%，自动触发信任降级。
第四，保护人才 pipeline：保留一部分"低效"的初级工作给人做，或者把 AI 产出当作教学材料而不是替代品。

## 风险与反方观点

**反方一：三元组/五维框架是事后归因。** 先看到 Coding 成功，再找五条理由，任何成功领域都能凑出五条。这个批评部分成立。回应是：五维不是解释历史，而是事前打分；它的价值在于能预测"哪个新领域会失败"，而不是给已成功的领域写传记。如果要检验，应该拿它去预测一个尚未规模化的领域（比如芯片验证、合成生物），看两三年后是否应验。

**反方二：SWE-bench 高分是刷分幻觉。** 静态算法题和独立仓库的成功，不代表企业级遗留代码的成功。这个批评成立，而且很重要。真实仓库缺测试、缺文档、充满隐式依赖，闭环会解体。所以本文把"绿地 Coding"和"遗留巨石"分开评分，前者 80%–90%，后者只有 30%–45%。

**反方三：模型变强会吞掉所有边界。** 长上下文、世界模型、工具调用可靠性提升，确实会改善 O、V、T 的部分环节。但 R 是物理规律，不是模型能力；C 是生物和时间尺度，也不是模型能力。模型能改善的是"预测"，不能改善"不可逆"。所以边界会移动，但不会消失。

**反方四：C 可以被 AI 压缩。** 如果 Agent 能读会议纪要、追踪决策链、代理跨部门沟通，协调成本可能下降。这个可能性存在，但目前没有可靠证据。更常见的情况是 AI 增加了沟通接口。本文的判断是：C 会下降，但速度远慢于 E，且下降的前提是接口标准化和责任可转移。

**反方五：组织摩擦是制度选择，不是铁律。** 同意。API Mandate 证明组织可以被改造。但改造的是边界和接口，不是人的判断和信任。把"组织不可代码化"理解成"组织不能改"，是过度解读。

**反方六：数据是相关性，不是因果。** GitClear 对 2.11 亿行代码的分析显示，AI 辅助编程普及后代码流失率上升近一倍、重复代码块约 10 倍；DORA 2024 显示 AI 采用率每提高 25%，交付稳定性下降约 7.2%、吞吐量下降约 1.5%。这两组数据与"技术债雪崩"一致，但不能单独证明因果——采用 AI 的团队可能本来节奏就更快、变更更频繁。引用时应保留这个限定。

**反方七：低估了"半形式化"领域。** 芯片设计、财务审计、工业配方都有形式化子集，可能比本文评分更早突破。这是最值得跟踪的反例。如果 EDA 在两年内跑到 85% 以上，说明五维评分对 V 的权重给低了。

## 跟踪指标与触发规则

| 指标 | 口径 | 预警阈值 | 触发动作 |
|---|---|---|---|
| 任务级成功率 | 端到端完成且通过验收的比例 | <70% | 缩小任务粒度，增加 oracle |
| 验证/生成时间比 | 人审+测试耗时 ÷ AI 生成耗时 | >2 | 该类任务停用 Agent |
| Spec 覆盖率 | 有可执行验收标准的变更占比 | <40% | 先补 Spec，不扩 autonomy |
| 线上逃逸率 | 门禁通过但线上出故障的比例 | 连续 2 周上升 | 信任降级，提高人工门禁 |
| Agent 引发的 P0 | 归因于 Agent 变更的 P0 数 | ≥1/季度 | 红区收紧，复盘门禁 |
| 人工介入率 | 需要人打断/接管的任务占比 | >50% | 检查工具抽象与上下文 |
| IoT 事故率 | 每千小时部署的物理事故 | 随部署量超线性上升 | 停止扩张，补传感器与兜底 |
| 数字孪生偏差 | 仿真预测与真机结果偏差 | >20% | 不用于策略训练 |
| 新人独立交付周期 | 初级工程师独立完成模块的时间 | 同比延长 >30% | 恢复初级任务，补人才 pipeline |

规则要写成可执行的 if-then，不要写成"加强管理"。例如：线上逃逸率连续两周上升，且门禁通过率仍高于 95%，则自动把所有黄区任务降为红区，直到逃逸率回落。

## 事实核查与批判性审查

> 本节逐条核查报告所依赖的关键说法。判定标准：只抓硬事实（日期、人物、定义、公式、单位、换算、算术、来源、A 当 B）；预测未兑现、数据截至某时点、观点分歧不算错误。

### 核查范围与方法

- **组织史时间线**：微软 stack ranking 的废除时间与宣布者。
- **代码质量与交付数据**：GitClear 的 2.11 亿行、流失率、重复代码，DORA 的 7.2%/1.5%，核对原报告口径与因果边界。
- **第三方逆向数字**：Claude Code 行数、文件数、utils 模块占比、“80% 是 harness”。
- **推演值**：Spec Coding 30% 接管、代码干净度超越 80% 人类。
- **简化框架的适用边界**：“知识—环境—纠错”三元组是否被当成普适定律。
- **跨领域概率**：表 1 的自主化概率是判断还是统计。

交叉核对方式：公司公告与公开报道、GitClear/DORA 原报告、源文章原文比对；相关性与因果分开；无实测的推演一律标 D。证据等级：A=原始披露或权威指南；B=多源一致；C=单一来源；D=推算或待核实。

### 待核实与证据边界

- **表 1 的跨领域自主化概率**（绿地 Coding 80%–90%、医疗 <10%、IoT 20%–30% 等）：全部是作者判断，不是统计；评分卡的分值也是经验标定。
- **“协调成本 C 占知识工作 50%–70%”**：没有统一测量，来自企业经验值；C 的比例直接决定 W=E+C 的解释力，属于关键假设。
- **BCG 与哈佛商学院 2023 年实验**（能力边界内质量提升约 40%、边界外正确率低约 19 个百分点）：需要核对样本、任务类型与“边界”定义；本文只作方向性引用。
- **桥水“近三分之一新人前两年离职”**：缺分母口径（全体新人、投资岗、某个年份），只能当量级参考。
- **“6 个月接管 30% 高频变更路径”**：工程推演，不是实测；正文已标“不是承诺”。
- **OGAS、亚马逊 API Mandate、Dot Collector 的细节**：来自公开史料与报道，具体数字和因果链有简化；用于提炼原则，不作史实考证。
- **“API 返回 200 但阀门没动”**：工程经验总结，不是统计比例；它说明的是虚假成功的机制，不是发生率。
- **SWE-bench 类基准与企业真实仓库的差距**：方向明确，具体差距缺统一测量。

### 对报告结论的影响

- **stack ranking 时间线修正改变案例的归因**：废除发生在鲍尔默任内，不是纳德拉的改革；因此不能把“废除强制排名”当成纳德拉文化改革的证据。案例的可迁移教训（量化人会诱发零和博弈）仍然成立，但历史叙述必须改。
- **Spec Coding 30%/80% 降级后，结论 6 只剩“规划值”**：6 个月接管 30% 是工程排期，不是能力承诺；“代码干净度超越 80% 人类”删除后，不能用它论证 AI 已接近人类工程师。Spec Coding 的适用条件（绿地、微服务、TDD 习惯）仍是核心。
- **GitClear/DORA 的因果限定不改变风险判断，但改变证据强度**：结论 8 和“技术债雪崩”的论证，不能只靠这两组相关性数据；更硬的依据是机制——遗留系统缺 oracle、缺测试，闭环解体。数据用于提示方向，不用于定量预测。
- **Claude Code 数字降级后，五维框架不受影响**：框架的依据是任务结构（O/V/R/T/L），不是某个工具的代码占比；“80% 是 harness”原本也只是旁证。
- **“一人公司”修正收窄了结论 4 的适用范围**：它只在一次性、低耦合、可验证任务成立；不能外推为“组织可以被无限压缩”。
- **三元组扩展为五维，直接改写结论 2**：三元组是数字世界的简化版，不是普适定律；这避免了“把一切业务代码化就能自动化”的错误推论。
- **需要打折的结论**：所有跨领域概率、C 的占比、BCG 的效应量、6 个月 30% 的排期，都是判断或推演；相对稳健的是机制层结论——pⁿ 衰减、物理不可逆、隐性知识、验证瓶颈、量化人的反作用。评分卡应作为立项讨论工具，不是预测模型。
